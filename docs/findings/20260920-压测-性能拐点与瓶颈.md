### 4.4 瓶颈层的直接证据(抢单 50 线程稳态,Arthas + MySQL 探针)

**(a) 一次 grab 的 108~119 ms 花在哪**(`trace TicketController grab`,压测 14 s 后附加,`results/arthas_trace_controller_grab_t50_steady.txt`):`TicketService.grab()` 107~119 ms,占请求 99.9%。

**(b) 事务代理三段的稳态分布**(`watch TransactionAspectSupport (invokeWithinTransaction|createTransactionIfNecessary|commitTransactionAfterReturning)`,240 个样本,`results/arthas_watch_tx_grab_t50_steady.txt`):

| 段 | 含义 | p50 | p90 | max |
|---|---|---|---|---|
| `createTransactionIfNecessary`(grab) | 从 HikariCP 拿连接 | **75.7 ms** | 83.0 ms | 86.0 ms |
| `invokeWithinTransaction`(record,嵌套的审计事务,不拿新连接) | 审计 INSERT 一趟 | 11.7 ms | 13.9 ms | 15.9 ms |
| `commitTransactionAfterReturning`(grab) | COMMIT(fsync)+ AFTER_COMMIT 里的 2 次 MQ 发送 | — | 16.2 ms | 19.3 ms |
| `invokeWithinTransaction`(grab,整段) | 上面三段之和 | 126.5 ms | 127.0 ms | 127.0 ms(n=4) |

无竞争时同一段是 12.3 ms(第三步测的),其中拿连接 0.4~0.9 ms。所以稳态下**每个请求约 75 ms 在等连接,约 30~40 ms 持有连接**;20 条连接 ÷ 0.03~0.043 s ≈ 460~660 tx/s,与观测到的 460~500 平台吻合。

**(c) MySQL 侧并不忙**(`tools/mysql_probe.py`,34 s 内每秒采 processlist,`results/grab_t50_mysql_probe.txt`):ticketqa 用户非 Sleep 连接数 **平均 2.1,峰值 7**;最常见状态 "waiting for handler commit"(平均 1.79 条)。同期 `Questions` 3110/s、`Innodb_os_log_fsyncs` 846/s;文件等待平均:`innodb_log_file` 325 µs、`binlog` 754 µs、`innodb_data_file` 421 µs。也就是说 20 条被 Hikari 标为 active 的连接,任一时刻只有 ~2 条在 MySQL 里执行,其余时间连接在 JVM 手里、等 Windows↔WSL 的网络往返和 fsync 返回。

**(d) 不是 JVM**:进程 CPU 各轮 ≤ 22%(均值 ≤ 10%),每轮 5~19 次 Young GC、最大停顿 ≤ 20 ms(仅 create_t10 头几秒),`threads_blocked` 全程 0。**不是 Tomcat**:线程按需涨到 306,没有排队指标(Tomcat 线程池指标本项目没暴露,见问题清单)。**不是挡板**:WireMock CPU 最高 81%,但 create 的 P99 增量与 Hikari pending 同步、与 WireMock CPU 不同步;grab 根本不经过挡板,平台高度却和 create 同量级。

### 4.5 瓶颈判断

**瓶颈在数据访问层:HikariCP 连接池(20)是节流阀,每事务的连接持有时间(稳态 30~43 ms)是分母。** 持有时间的构成里 MySQL 执行本身只占一小部分(单条语句 0.1~1 ms),大头是每条语句一次 Windows→WSL 往返(一次 grab 事务 4 条语句 + COMMIT + 2 次 MQ 发送 = 7 次跨 VM 往返)和 COMMIT 的 fsync(`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`)。MySQL 容器 CPU 75~99% 是**单核**打满(4 vCPU 里的一个),对应的是 3000+ 语句/s 的协议处理和 fsync 的系统调用,不是查询计算——所有语句都走主键,`rows_examined=1`。

这个结论的边界:它是"这台机器上、JVM 在 Windows、MySQL 在 WSL2 的 4 vCPU 虚拟机里"的瓶颈。同一份代码放到服务与 MySQL 同网段的 Linux 上,每次往返从 ~1 ms 降到 ~0.1 ms,连接持有时间会缩短数倍,平台会上移,拐点档位也会变;但"池大小 × 1/持有时间 = 上限"这个结构不变。

## 5. 顺带发现

### 5.1 MQ 消费端跟不上生产端(异步链路的容量缺口)

- `q.ticket.status-changed` 只有 1 个消费者,每条消息一次去重表 INSERT + 处理,实测消费速率 **≈ 190 条/s**(19:14:11→19:17:04 积压 33488→0,3 分钟;两个队列同时消费时合计 ≈ 340 条/s)。
- 创建链路 10 线程(151 QPS)时消费 == 生产;20 线程(271 QPS)起开始积压:各轮结束时队列积压 8540 → 23423 → 35905 → 52279 条(`results/create_t*_env_after.md`)。
- 抢单每次发 2 条(STATUS_CHANGED + ASSIGNED),460 QPS ≈ 920 条/s;60 s 的 grab_t100 生产 59144 条只消费了 6671 条——消费者的去重 INSERT 也要从同一个 HikariCP 池拿连接,池被 HTTP 请求占满时消费者一起挨饿,消费速率从 190/s 掉到 ~110/s。
- 影响:通知延迟以分钟计(拐点之后每压 1 分钟约要 3 分钟消化);"消息不丢"在容量层面成立(积压最终都消费了),但"及时"不成立。

### 5.2 SLA 调度器的升级吞吐

`scan-interval-ms=30000`、`scan-batch-size=100` → 最多 200 张/分钟。创建链路造出 27190 张 P0 单在 19:20 后集中到期,调度器从 19:20 跑到 21:41 累计 441 轮 / 29975 张,积压仍有 36343 张(`results/grab_t50_watch_env_before.md`)。一次到期高峰要几个小时才能升级完,期间 `sla_deadline` 已过而状态仍是 PENDING/ASSIGNED,SLA 承诺是静默失守的。这是配置容量问题,不是正确性问题(去重和闭区间语义都对)。

### 5.3 `ticket_no` 生日碰撞 → 创建 500(create_t200 的 2 个错误)

- 现象:200 线程那轮 2 个 `HTTP 500 / 50000`,traceId `3e4fe12473cc40a8` 等;`stdout.log` 里 `SQLIntegrityConstraintViolationException: Duplicate entry 'T20260920-33818501' for key 'ticket.uk_ticket_no'` 和 `'T20260920-40AD0748'`。
- 根因:`TicketService.newTicketNo` = `"T" + yyyyMMdd + "-" + UUID.randomUUID().toString().substring(0, 8)`——每天只有 32 bit 随机量。当天累计创建 ~9 万张时,生日碰撞期望 ≈ n²/(2·2³²) ≈ 0.9 次,实测 2 次。
- 影响:客户的一次提交直接 500,工单没落库,而 LLM 已经调过一次。日均几万单的量级下这是必然事件,不是偶发。

### 5.4 环境层面的两个坑(已修 / 已记)

- Prometheus 容器抓不到宿主机服务:WSL2 里 `host-gateway` 解析成 docker0(172.17.0.1)而不是 Windows;加了 `ops/docker-compose.wsl.yml` 用 WSL 默认网关(172.30.192.1)覆盖 `extra_hosts`。
- 抢单 id 池第一版混入了 group 2 的单(创建脚本 groupId 随机 1/2),坐席 3/4 抢到 403;这两轮已作废(`results/invalid/`),导出改为只取 group 1。

## 7. 结论

- 预期 vs 实际:确有拐点——创建 20→50 线程、抢单 10→20 线程;之后 QPS 平台 365 / 460~500,P99 线性上升。
- 瓶颈层:数据访问层(HikariCP 20 条连接 × 每事务 30~43 ms 持有时间),持有时间由跨 VM 往返和 fsync 主导;JVM、Tomcat、GC、挡板都不是。
- 发现缺陷:`ticket_no` 生日碰撞(500);MQ 消费端容量缺口(积压);SLA 升级吞吐上限(积压数小时)。
- 修复 / 调优建议(只写不做):
  - 抢单链路把 AFTER_COMMIT 的 MQ 发送移出连接持有期(先释放连接再发,或用 outbox)——直接缩短 30~40% 的持有时间;
  - `ticket_no` 换成雪花 / 自增序列 / 至少 64 bit 随机;
  - MQ 消费者并发 `concurrency` > 1 且消费者用独立的小连接池,避免和 HTTP 请求争同一个池;
  - SLA `scan-batch-size` 与间隔按日均到期量重算,或到期高峰时循环扫到空;
  - 池大小调到多少要在服务与 MySQL 同网段的环境重测,本机数字不能直接外推。
