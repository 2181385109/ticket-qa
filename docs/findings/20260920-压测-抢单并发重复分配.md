- 被测接口:`POST /api/tickets/{id}/grab`(`TicketService.grab`)

- **最小复现并发数 = 2,复现率 5/5**;梯度全部 12 轮 12/12 复现。
- 三个对账关系:① 200 的个数 == 审计 ASSIGNED 行数(HTTP 层与库"自洽",所以只看响应发现不了);② 每张单只真正发生过一次 `PENDING→ASSIGNED`,其余 N-1 次是 `ASSIGNED→ASSIGNED` 的覆盖;③ 终值 `assignee_id` = 最后一个拿到行锁的人。
- ≥20 线程后成功数封顶在 12~14 而不是线程数——原因不在被测逻辑,在连接池,见配套记录。

### 4.4 持锁演示(把窗口拉长到肉眼可见)

组长会话 18:44:08.318 `BEGIN; UPDATE ticket SET assignee_id=2, status='ASSIGNED' WHERE id=8241;` 持锁 45 s。18:44:11 发 5 个 grab:5 个都读到 PENDING(SELECT 非锁定读),在 UPDATE 上等行锁;组长 18:44:53.327 提交后,5 个 UPDATE 在 53.536~53.564 依次执行,5 个响应全部 200、各自 `assignee=自己`,终值 assignee=3——**组长的手动指派也被覆盖了**。slow log 里 5 条 UPDATE 的 `lock_time` = 42.75~42.84 s。文件:`results/lockhold_*`。

## 5. 根因

**check-then-act 竞态。** `TicketService.grab` 第 216 行 `getOrThrow(id)` 是 REPEATABLE-READ 下的一致性非锁定读(slow log `lock_time` 1~5 µs),第 218 行在内存里判断 `status == PENDING`,第 224 行 `updateById` 才对行加 X 锁。任何在第一个事务 COMMIT 之前拿到数据库连接并执行了 SELECT 的线程,都会读到 PENDING、通过判断、排进行锁队列,锁一释放就逐个覆盖。

### 5.1 窗口实测宽度(Arthas `watch` Hikari `ProxyPreparedStatement.execute` / `ProxyConnection.commit`)

| 条件 | SELECT 发出 → COMMIT 返回 | 组成 |
|---|---|---|
| 无竞争,1 线程(5 次中 2 次完整采到,ticket 8243 / 8244) | **13.1 ms / 12.3 ms** | SELECT 1.3 → JVM 内 2.4(MyBatis 映射 + mapper DEBUG 日志 + 状态机;`checkGrab` 本身 0.03)→ UPDATE 1.6 → 审计 INSERT ≈2 → COMMIT 3.5 |
| 20 线程竞争(ticket 8238,池内 19 条连接) | 第一个事务 **28.8 ms**;后续线程 37 → 50 → 60 → … → 164 ms 线性递增 | 20 个 SELECT 在 +550~+569 全部返回 PENDING;第一个 COMMIT +579;UPDATE 返回每 ~10 ms 一个(= 前一持锁者的 INSERT + COMMIT) |
| 100 线程(ticket 8240,MySQL slow log µs 级) | 20 条 UPDATE 在 13 ms 内全部发出,逐个完成 | `lock_time` 阶梯 0 → 18.3 → 25.0 → 31.3 → 40.9 → … → 226.1 ms;每条 UPDATE 的 `query_time` ≥ 97% 是 `lock_time` |

COMMIT 3.5 ms 里的大头是 fsync:MySQL `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`(performance_schema 统计 `wait/io/file/sql/binlog` 平均 754 µs、`innodb_log_file` 325 µs,再加 Windows→WSL 的往返)。**换成 `=2` / `=0` 或换更快的盘,窗口会变窄;竞态是逻辑缺陷,不会因为配置变化消失,只是复现的时间窗口跟着变。**

### 5.2 排除项

| 怀疑 | 证据 | 结论 |
|---|---|---|
| 索引缺失拉长窗口 | `EXPLAIN` SELECT → `type=const key=PRIMARY rows=1`;UPDATE → `type=range key=PRIMARY rows=1`;`events_statements_summary_by_digest`:grab 的 UPDATE 201 次共 17.07 s,其中 16.9 s 是 `SUM_LOCK_TIME`(`results/mysql_explain_grab_path.txt`) | 排除。窗口里没有一毫秒花在找行上 |
| JVM 锁竞争 | 持锁期间 `thread -b` → "No most blocking thread found!";`thread --state BLOCKED` → 0;jcmd 线程栈里 5 个 grab 线程全部 RUNNABLE 停在 `NioSocketImpl.read ← ClientPreparedStatement.execute ← TicketService.grab:224`(`results/jcmd_threadprint_lockhold.txt`) | 排除。线程在等 MySQL 回包,不是在等 Java 锁 |
| GC 停顿 | `gc-20260920-175426.log`:整个会话 28 次停顿,中位 8.2 ms,最大 25.6 ms(基线压测期间);12 轮梯度(18:01:24~18:03:08)和 5 轮 2 线程复现的窗口内 **0 次 GC**;两次落进 burst 的 GC(18:30:57.343 17.6 ms、18:41:37.757 16.2 ms)都发生在第一次 COMMIT 之后 | 排除 |
| 行锁等待超时 | `innodb_lock_wait_timeout=50 s`,最长等待 226 ms(持锁演示 42.8 s 也远未触及) | 不参与 |

## 6. 结论

- 预期 vs 实际:预期只有 1 个 200;实际 2 线程即 100% 复现,N ≤ 池内连接数 + 1 时 N 个全部 200。
- 缺陷:是。`assignee_id` 被覆盖,组长指派也会被覆盖;通知消费者收到 N 条"已分配"消息。
- 为什么 2 就是临界点:两个线程只要都在第一个 COMMIT 之前完成 SELECT 就复现;无竞争时这个窗口是 12~13 ms,而集合点放行的两个请求的 SELECT 相差 < 1 ms。它不需要"高并发",只需要两个请求的间隔小于一次事务的长度。
- 修复建议(只写不做,留下一阶段):
  1. 把判断放进 UPDATE:`UPDATE ticket SET status='ASSIGNED', assignee_id=? WHERE id=? AND status='PENDING'`,`affected rows == 0` 即抛 `IllegalTransitionException`。一条语句,零额外依赖,是这类"状态跃迁"最直接的写法;
  2. 或乐观锁 `version` 列(MyBatis-Plus `@Version`),失败重试或直接 409;
  3. 或 `SELECT ... FOR UPDATE` 把读升级为锁定读——代价是把所有抢单串行化在锁上,吞吐会掉;
  4. 分布式锁(Redis)不推荐:本项目 Redis 是 fail-open 的加速器(见故障注入记录),用它做正确性保障与 ADR 的定位冲突。
  修完后 `tests/perf/grab_race.jmx -Jthreads=20` 应稳定得到 1 个 200 + 19 个 409,审计恰 1 条 ASSIGNED。
