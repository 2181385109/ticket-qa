## 2. 抢单竞态回归(`tools/regress_grab.sh`)

### 2.1 同档位重跑

每轮:`grab_race.jmx -Jthreads=N`(setUp 新建 1 张 PENDING 单 → N 个坐席线程集合点同时 grab)→ `grab_evidence.py` 查库。
新增两列指标差值:三层防线各自拦下了多少。

| 轮次 | 线程 | 压测前池 total | HTTP 200 | HTTP 409 | 审计 ASSIGNED 行数 | 审计序列连续 | Δlock_acquired(进库) | Δlock_rejected(Redis 挡) | Δdb_conflict(条件更新 0 行) | 工单 |
|---|---|---|---|---|---|---|---|---|---|---|
| r1 | 2 | 2 | **1** | 1 | **1** | YES | 1 | 1 | 0 | 4334 |
| r2 | 2 | 2 | **1** | 1 | **1** | YES | 1 | 1 | 0 | 4335 |
| r3 | 2 | 2 | **1** | 1 | **1** | YES | 1 | 1 | 0 | 4336 |

| r5 | 2 | 2 | **1** | 1 | **1** | YES | 1 | 1 | 0 | 4338 |
| r1 | 20 | 3 | **1** | 19 | **1** | YES | 1 | 19 | 0 | 4339 |
| r1 | 100 | 3 | **1** | 99 | **1** | YES | 2 | 98 | 0 | 4340 |

修复前同档位:2 线程 2 个 200(5/5 轮),20 线程 12 个,100 线程 14 个;审计 ASSIGNED 行数 = 200 的个数。

读法:100 线程那轮进库 2 个——第一个提交并释放 Redis 锁后,恰好有一个还在排队的请求拿到了锁,进库 SELECT 读到 ASSIGNED,
在内存判断处就以 40901 返回,没走到条件更新(db_conflict 0)。其余 98 个在拿到数据库连接之前就被 Redis 锁挡回。

全库扫描 `to_status='ASSIGNED'` 多于 1 行的工单:0 行(修复前梯度后是 12 张全部命中)。

### 2.2 Redis 停机下重跑——证明条件 UPDATE 单独就能保证正确

`docker compose stop redis` 后(health DOWN,`grab_lock_unavailable_total` 每请求 +1,fail-open 全部进库):

| 线程 | HTTP 200 | HTTP 409(全部 40901) | 审计 ASSIGNED 行数 | 序列连续 | Δlock_unavailable | Δdb_conflict | 工单 |
|---|---|---|---|---|---|---|---|
| 20 | **1** | 19 | **1** | YES | 20 | 合计 11(两轮) | 4341 |
| 100 | **1** | 99 | **1** | YES | 100 | ↑ | 4342 |

120 个请求全部进库、全部执行了 SELECT,其中 11 个在第一个事务提交前读到 PENDING、走到了条件更新,
都拿到 0 行;其余 109 个 SELECT 时已是 ASSIGNED。这就是 ADR-016 的核心论点:**Redis 锁拿掉,正确性不变,只是多 11 个请求进库。**
修复前同样条件(无锁、全部进库)是 12~14 个 200。

### 2.3 为什么这次不再提"成功数 = 池大小 + 1"

修复前成功数是池状态的函数(KI-010);修复后 7 + 2 轮里池从 2 到 20、Redis 从有到无,成功数恒为 1。
"修好了"的定义是结果不再依赖那个隐藏变量,不是某一次跑出了 1(ADR-021)。

## 3. 审计序列连续性

取证脚本 `grab_evidence.py` 新增第四条 SQL 的结论字段:按 id 排序后第 k 行 `to_status == 第 k+1 行 from_status`,
且终态 `ticket.status == 最后一行 to_status`。上表 9 轮全部 YES。修复前 2 线程那轮(8225)的审计是
`NULL→PENDING, PENDING→ASSIGNED(4), PENDING→ASSIGNED(3)`,第 2 行 to=ASSIGNED ≠ 第 3 行 from=PENDING,断裂。

修复后一张 100 线程工单(4340)的完整审计:

```
#7413  NULL     -> PENDING   operator=1  LLM     自动分类 ...
#7414  PENDING  -> ASSIGNED  operator=3  MANUAL  抢单
终态 status=ASSIGNED assignee_id=3 version=1
```

接口自动化里对应:`tests/api/framework/audit.py::assert_audit_chain`(每个并发用例都跑)+
`test_audit_chain.py::test_no_broken_chain_in_database`(全库最近 2000 张)。压测工具 `reset_grabbed.py` 改为重置时补一条
`ASSIGNED→PENDING(perf reset)` 审计,否则工具自己会制造断裂。

### 4.2 差异的来源

- 抢单每次多两次 Redis 往返(SET NX + Lua DEL)。低并发下这是纯增量:t10 平均 21.7 → 23.3 ms(+1.6 ms),
  与两次 Windows↔WSL 往返(每次 ~0.7 ms)吻合;高并发下请求在等 HikariCP 连接的时间占主导,Redis 往返被淹没,t100 QPS 几乎不变。
- 创建链路没有碰 Redis(锁只在 grab 上),−2.4%~−5.0% 的差异更可能是背景差异:修复后 create_t10 起跑时池 11/11
  (前一小时的竞态回归撑起来的)vs 修复前 3/3;修复后 create_t20 起跑时堆已用 621 MB(前一轮遗留)vs 修复前更低。
  4% 在两轮压测的正常抖动范围内(修复前 create_t100 与 t200 QPS 完全相同 364.7,说明平台本身很稳,
  但轮与轮之间的头几秒受池 / 堆状态影响)。**不把这 4% 当成修复的代价,也不当成噪声一笔勾销**——要坐实需要同一状态下 A/B 各跑三轮,留给平台层的基线对比。
- grab_t200 的 45 × 409 消失:修复前是 SLA 调度器把 id 池里的单升级成了 ESCALATED;修复后抢单梯度期间没有到期单(§1 第二点)。

## 5. 读链路的拐点(问题清单第 6 条,新增 `ticket_read.jmx`:详情 GET → 列表 GET(status 过滤 + 分页)→ PUT 改标题,id 轮询)

库里 87190 张单(53487 PENDING)时:

| 线程 | 采样 | 合计 QPS | detail p50 / p99 | **list p50 / p99** | update p50 / p99 |
|---|---|---|---|---|---|
| 10 | 3149 | 157 | 3 / 17 ms | **152 / 307 ms** | 16 / 74 ms |
| 50 | 3250 | 161 | 120 / 324 ms | **453 / 800 ms** | 152 / 357 ms |
| 100 | 3296 | 159 | 187 / 606 ms | **520 / 1050 ms** | 196 / 566 ms |

- 读链路 **10 线程就到平台**:合计 ≈158 QPS,每个采样器 ≈53/s;50、100 线程 QPS 不涨,延迟线性上升——典型的"某一步是串行瓶颈"。
- 瓶颈是列表接口:`selectPage` 的 `COUNT(*) ... WHERE status='PENDING' AND deleted=0` 走 `idx_ticket_status_sla` 扫 43120 条索引项再回表核对 `deleted`
  (`EXPLAIN`:`type=ref rows=43120 filtered=10% Using where`),每次 ~150 ms 的 CPU 在 MySQL 单核上串行,53 次/s 就是一核的上限。
  数据页 `SELECT ... ORDER BY id DESC LIMIT 20` 本身是 `Backward index scan` 40 行,不是问题。
- 详情和修改在 10 线程下分别 3 ms / 16 ms,修改带乐观锁 `WHERE id=? AND version=?`,0 个 409(id 池 4 万张,两个线程同时改同一张的概率可忽略)。
- 登记为 **KI-017**:列表接口的 COUNT 与数据量线性相关,10 万张单时单核 53 次/s。选项:覆盖索引 `(status, deleted, id)` 让 COUNT 不回表、
  或列表不返回精确 total(游标分页)、或 total 走缓存。这是读链路和写链路**不同的瓶颈来源**(写链路瓶颈是连接持有时间,读链路是单条 SQL 的 CPU),
  留待后续决定;本轮不改。
