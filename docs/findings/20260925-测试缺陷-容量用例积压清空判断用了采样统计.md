# 2026-09-25 · 测试自身缺陷:容量用例用 RabbitMQ 采样统计判断"积压已清空"

> 类型:**测试缺陷,不是产品缺陷**。消息没有丢、消费者没有被饿死;是用例在消费完成之前就去做了最终断言。
> 记录方式:本仓库只写真实跑出来的结果;下面每个数字都来自本机 2026-09-25 的运行,复现命令见 §4。

## 1. 现象

`tests/api/test_capacity.py::TestConsumerStarvation::test_consumer_not_starved_when_pool_saturated` 在本机偶发失败,失败点是最后一条断言:

```
assert metrics.delta(metrics_before, "mq_event_consumed_total") >= metrics.delta(metrics_before, "mq_event_published_total")
```

2026-09-25 首次发现于提示词注入任务 M4 的全量回归(池 20),随后按 ADR-023 在池 3 下单独重跑仍失败(消费 61 / 发布 1324)。

## 2. 根因

用例在最终断言之前用 `wait_until(rabbit.queue_depth("STATUS_CHANGED") == 0)` 判断"积压清空"。`queue_depth` 读的是 RabbitMQ 管理接口
`/api/queues/{vhost}/{queue}` 的 `messages` 字段——这是管理插件按 `collect_statistics_interval`(默认 5 s)**采样**的统计,不是实时值。
负载刚停时它可能还是旧样本里的 0,于是等待立即返回,最终断言拿到的是消费者还在处理途中的计数。

证据(均为本机池 3、挡板模式):

| 观察 | 值 |
|---|---|
| 修改前第 2 次运行 | 总耗时 9.14 s 就失败(8 s 负载 + 几乎为零的"清空"等待),消费 74 / 发布 1240 |
| 修改前第 3 次运行 | 消费 899 / 发布 1298 |
| 修改前 3 次跑完**当时**的累计指标 | `mq_event_consumed_total` 2556,`mq_event_published_total` 3600 |
| 约 20 s 后再读 | `mq_event_consumed_total` 3600 = `mq_event_published_total` 3600,`mq_event_duplicate_total` 0;三个队列 `messages / ready / unacked` 全为 0 |

也就是说:消息全部被消费了、没有重复,只是比用例的最终断言晚到。

## 3. 处置

只改"判断积压已清空"这一步:等待条件改成**服务自己的计数**——`mq_event_consumed_total` 的增量追平 `mq_event_published_total` 的增量,超时 60 s(与原来一致)。

- 核心断言不变:`max_pending() > 0`(前提:池被打满)、`rate_during > 0`(池满期间消费者没被饿死)、最终的消费 ≥ 发布 三条原样保留。
- 没有改"队列起点为空"那一步(同样读采样统计,但它只影响起点,且任务范围只授权改清空判断);若日后它也造成偶发,同样改成计数比对。
- 不编 KI 号:KI 记录的是被测服务的问题,这是用例自身的问题。

## 4. 修改前后(本机,`HIKARI_MAX_POOL_SIZE=3`,挡板模式,单独运行该用例)

| | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 修改前 | passed(21.52 s) | **failed** 74 < 1240(9.14 s) | **failed** 899 < 1298(18.19 s) |
| 修改后 | passed(16.98 s) | passed(16.81 s) | passed(19.88 s) |

