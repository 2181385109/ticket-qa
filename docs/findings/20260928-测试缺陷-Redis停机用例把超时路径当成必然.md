# 2026-09-28 测试缺陷 · Redis 停机用例把"等满超时"这一条路径当成了必然

> 记录类型:测试自身缺陷(不编 KI 号)。证据来自 GitHub Actions 的真实运行记录、CI 上传的 Allure 原始结果与服务日志,以及本地保存的服务日志。
> 改断言语义前已把证据与方案交作者,作者 2026-09-28 确认(并把上界改为"每一次 ≤ 1500 ms"、要求优先用指标)。

## 1. 现象

CI run 36433276730(main 52eafb2),`api/test_fault_injection.py::TestRedisOutage::test_fail_open_and_recovery_within_slo`:

```
>               assert degraded >= 800, f"预期每请求 +~1 s,实际 {degraded:.0f}ms(基线 {baseline:.0f}ms)"
E               AssertionError: 预期每请求 +~1 s,实际 9ms(基线 2ms)
```

同一用例在 run 35566646552(a4c21d7)、36308295948(v0.6)通过,停机期间 `/me` 为 1005~1008 ms;v0.5 的 run 36308296066 失败于同一断言(`实际 5ms`)。

## 2. 注入是否生效:生效了

- Allure 附件(`docker compose stop redis`):`[0.3s exit=0] Container ticketqa-redis Stopping / Stopped`;`start` 同样 exit=0。用例没有调用 `compose ps`,没有这份输出。
- 用例在延迟断言之前的两条断言都通过:health 503、`components.redis` = DOWN。
- 服务日志(CI 上传的 `service-logs`),停机期间 3 次 `/me` 各有一对:
  ```
  14:11:34.258 WARN [cbc2869f4cee4fd5] … CacheConfig : 缓存读取失败,回源查库 cache=agents key=1 err=Redis exception
  14:11:34.264 WARN [cbc2869f4cee4fd5] … CacheConfig : 缓存写入失败,忽略 cache=agents key=1 err=Redis exception
  ```
  请求都是 200。即:**Redis 停了,服务 fail-open 了,只是每次缓存操作约 2 ms 就失败**,而不是等满 500 ms。

## 3. 为什么这次快:Lettuce 的两条断连路径

| | 通过的 run 36308295948 | 失败的 run 36433276730 |
|---|---|---|
| stop 后首次重连(约 +0.2 s) | `Cannot reconnect … Connection refused` ×2 | `Connection reset`(`SocketChannelImpl.read` 抛出,TCP 已建立后收到 RST)+ `Connection closed prematurely`(`RedisHandshakeHandler.channelInactive`) |
| 缓存操作的失败原因 | `err=Redis command timed out` ×12 | `err=Redis exception` ×6 |
| 停机期间 `/me` | 1007 / 1004 / 1004 ms | 14 / 7 / 6 ms |

对照 Lettuce 6.3.2 源码(`io.lettuce.core.protocol`):

1. 已建立的通道上出现异常 → `CommandHandler.exceptionCaught`;通道未处于连接状态时调用 `endpoint.notifyException(cause)`。
2. `DefaultEndpoint.notifyException`:`if (!isConnected()) connectionError = t;`
3. 此后 `writeToBuffer` / `writeToDisconnectedBuffer` 里 `if (connectionError != null) command.completeExceptionally(connectionError)`——命令**立即**失败,
   直到下一次 `notifyChannelActive` 清掉 `connectionError`。Spring 的 `LettuceFutures` 把它包成普通 `RedisException`,转换为 `RedisSystemException("Redis exception")`,
   `CacheConfig.errorHandler` 照常当作未命中、回源查库。
4. `Connection refused` 发生在建连之前,不经过通道管道,`connectionError` 不被设置 → 命令进断连缓冲区,等满 `spring.data.redis.timeout`(500 ms)→ `Redis command timed out`;
   `/me` 一次 get + 一次 put,约 1 s。

同一时间的健康检查(另一条连接)仍是 `Command timed out after 500 millisecond(s)`,与"只有收到 RST 的那条连接被设了 connectionError"一致。

**是谁在 Redis 进程退出后接受了 TCP 连接并发 RST——推断**:容器拆除过程中短暂仍在监听 6379 的 docker-proxy(端口映射的用户态代理)。
日志只能证明"连接被接受后被重置",不能证明是谁;这是推断,没有直接证据。

## 4. 本地为什么一直是约 1 秒

本地保存的服务日志(`service/logs/` 当前文件与全部 `.gz` 归档)里:重连失败 `Connection refused` 28 次、`Connection closed prematurely` 22 次,`Connection reset` 0 次;
`cache=agents` 的缓存失败 450 次**全部**是 `Redis command timed out`。本地重连要么被拒绝,要么被对端正常关闭(推断:WSL 的 localhost 转发接受连接后正常关闭),
都没有在已建立的连接上收到 RST,所以从没走到立即失败的路径。
所以"约 1 秒"不是 WSL 特有:CI 上多数时候也是 1 秒;快速失败只在首次重连恰好撞上 RST 时出现,是时序竞争。

## 5. 与 ADR 是否一致

ADR-020、README §9、[20260920-故障注入记录](20260920-故障注入记录.md) 都把"每请求 +1 s"写成**代价**("代价如设计"),没有写成保证;
立即失败再回源更快,功能上是同一个 fail-open。所以这不是被测服务的问题,不登记 KI。

## 6. 修改(只改这一条用例)

- 去掉:`degraded >= 800`。
- 核心断言:**fail-open 确实发生**。服务**没有**缓存失败相关的指标(`CacheConfig.errorHandler` 只打日志;全仓自定义 Micrometer 指标只有 MQ、SLA、抢单锁 / 并发冲突、LLM 几组,没有缓存相关的),
  所以观测点是服务文件日志:停机前记下日志偏移,停机期间 3 次 `/me` 都必须 200,且每次都能按 `[traceId]` 对上一行 `缓存读取失败,回源查库 cache=agents`,
  其 `err=` 只能是 `Redis command timed out` 或 `Redis exception`。
- 新增上界:停机期间**每一次** `/me` ≤ 1500 ms(get + put 各 ≤ 500 ms 超时 + 余量;不用平均值,平均会掩盖单个请求挂住)。防的是超时配置失效后缓存操作挂住(Lettuce 默认命令超时 60 s)。
- 记录:Allure 附件"Redis 停机:fail-open 路径与耗时"写基线、逐次耗时、本次路径(timed out / Redis exception)与对应日志行。
- 不变:health 503 且 redis DOWN、抢单成功、`grab_lock_unavailable_total` +1、`grab_lock_acquired_total` +0、`sla_scan_lock_unavailable_total` ≥ 1、恢复 ≤ 45 s SLO、恢复后 < 200 ms。
- 服务日志不可用(`SERVICE_LOG_PATH` 未配或文件不存在)时用例直接失败,不 skip——核心断言依赖它。

**依赖的日志格式**(改了日志就要改用例):文件日志每行带 `[traceId]`(logback file pattern,KI-016);`CacheConfig` 的 WARN 消息
`缓存读取失败,回源查库 cache={} key={} err={}` 以 `err=<异常消息>` 结尾;异常消息是 Spring Data Redis `LettuceExceptionConverter` 的固定文案。

## 7. 验证

- 本地(WSL Docker + 挡板模式服务,当前代码重新打包):该用例通过,路径 `['timed out', 'timed out', 'timed out']`,`/me` 1019 / 1027 / 1019 ms,恢复 7.8 s。
- 快速失败路径本地无法按需复现;用 CI run 36433276730 的真实服务日志离线核对:3 个 traceId 都匹配到日志行,分类为 `Redis exception`,耗时 14 / 7 / 6 ms ≤ 1500——新断言下该次运行会通过。
