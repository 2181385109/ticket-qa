# 联调发现:JDK HttpClient 的 h2c 升级让所有 LLM 调用静默降级

> 记录类型:联调发现(非压测、非故障注入)。所有数据均来自 2026-09-20 本机联调的真实输出,
> 无预测、无模拟。复现代码见文末,可在任何一台起了 WireMock 容器的机器上重跑。

| 项 | 值 |
|---|---|
| 日期 | 2026-09-20 04:04(首次启动服务)~ 04:08(修复验证) |
| 服务版本 | v0.1-service 联调中间态(修复提交在 `dd1c436 service: ...` 之前) |
| 运行方式 | Windows 宿主 `java -jar target/ticket-qa-service-0.1.0.jar`;MySQL / Redis / RabbitMQ / WireMock 在 WSL2 Ubuntu-24.04 的 Docker 里 |

## 1. 现象:一切"看起来正常"

第一次跑 `ops/smoke/smoke_api.py`,创建工单的三条基线全部 201,分类结果和预期一致:

```
[create REFUND]      POST /api/tickets -> HTTP 201  352ms   category=REFUND priority=P1
[create TECH/P0]     POST /api/tickets -> HTTP 201   48ms   category=TECH   priority=P0
[create OTHER group2]POST /api/tickets -> HTTP 201   61ms   category=OTHER  priority=P2
    分类断言通过: REFUND/P1, TECH/P0, OTHER/P2
```

接下来两条降级路径的用例露出了破绽——但破绽很小:

```
[[SLOW] -> timeout -> rules]  POST /api/tickets -> HTTP 201  36ms   category=REFUND
[[BAD_CATEGORY] -> OTHER]     POST /api/tickets -> HTTP 201  41ms   category=BILLING   ← 断言失败
```

- `[SLOW]` 应该被挡板延迟 5 秒、服务在 3 秒超时后降级,耗时应 ≥ 3000ms;实际 **36ms**。
- `[BAD_CATEGORY]` 挡板应返回 `SPAM`、服务契约校验后落 `OTHER`;实际 **BILLING**——正好是
  标题"账单问题"按关键词规则算出来的结果。

如果冒烟脚本只断言"分类在枚举内"(这是 LLM 路径测试的常规写法,见 walkthrough 第 10 节),
这两条都会通过。**前三条基线的分类之所以"正确",是因为关键词规则和挡板规则用了同一套
关键词**——降级路径给出了和正常路径一模一样的答案。

## 2. 怎么发现的:`llm_call_log.degraded = 1`

没有看接口响应,直接查调用记录表:

```
SELECT id, ticket_id, scene, request_model, response_model, latency_ms, degraded, degrade_reason, raw_category, final_category
  FROM llm_call_log ORDER BY id;

id  ticket_id  scene     request_model       response_model  latency_ms  degraded  degrade_reason  raw_category  final_category
1   1          CLASSIFY  mock-classifier-v1  NULL            120         1         UPSTREAM_ERROR  NULL          REFUND
2   2          CLASSIFY  mock-classifier-v1  NULL            6           1         UPSTREAM_ERROR  NULL          TECH
3   3          CLASSIFY  mock-classifier-v1  NULL            5           1         UPSTREAM_ERROR  NULL          OTHER
4   4          CLASSIFY  mock-classifier-v1  NULL            5           1         UPSTREAM_ERROR  NULL          REFUND
5   5          CLASSIFY  mock-classifier-v1  NULL            6           1         UPSTREAM_ERROR  NULL          BILLING
```

**5 条全部 `degraded=1`、`degrade_reason=UPSTREAM_ERROR`、`response_model=NULL`、`raw_category=NULL`。**
也就是说从服务启动开始,没有任何一次 LLM 调用真正成功过——所有"分类结果"都是关键词规则给的。
接口层面零错误、HTTP 全 201。

同一时刻的 Prometheus 指标(`/actuator/prometheus`)也印证:`llm_fallback_total{reason="UPSTREAM_ERROR"}`
= 5,`llm_circuit_open_total` = 1——第 5 次失败已经把熔断器打开了,后续调用连 HTTP 请求都不发。

## 3. 排查路径

**第一步:看服务日志里降级的原因。** `LlmService` 在每次失败时打 WARN:

```
04:04:19.825 WARN  LLM 调用失败 scene=CLASSIFY reason=UPSTREAM_ERROR latency=120ms consecutiveFailures=1 msg=LLM 网络错误: EOF reached while reading
04:04:19.996 WARN  LLM 调用失败 scene=CLASSIFY reason=UPSTREAM_ERROR latency=6ms   consecutiveFailures=2 msg=LLM 网络错误: Received RST_STREAM: Stream cancelled
04:04:20.056 WARN  LLM 调用失败 scene=CLASSIFY reason=UPSTREAM_ERROR latency=5ms   consecutiveFailures=3 msg=LLM 网络错误: Received RST_STREAM: Stream cancelled
04:04:20.108 WARN  LLM 调用失败 scene=CLASSIFY reason=UPSTREAM_ERROR latency=5ms   consecutiveFailures=4 msg=LLM 网络错误: Received RST_STREAM: Stream cancelled
04:04:20.146 WARN  LLM 调用失败 scene=CLASSIFY reason=UPSTREAM_ERROR latency=6ms   consecutiveFailures=0 msg=LLM 网络错误: Received RST_STREAM: Stream cancelled
04:04:20.147 ERROR LLM 熔断打开,至 ... 前所有调用直接走规则
```

两个关键词:第一次是 `EOF reached while reading`(连接被对端关了),之后全是
`Received RST_STREAM: Stream cancelled`。**`RST_STREAM` 是 HTTP/2 的帧名**——而我们的挡板
地址是 `http://localhost:8089`,明文 HTTP,按理没有 HTTP/2。

**第二步:看挡板收到了什么。** WireMock 的请求日志 `GET /__admin/requests`:

```
REQ POST /mock/llm/classify | Content-Type: application/json | body: (空)
   matched: True | stub: classify | 兜底 → OTHER / P2
(× 5,全部一样)
```

挡板确实收到了 5 个请求,但**请求体全部为空**,于是命中了兜底桩、返回 200 + OTHER。
矛盾出现了:挡板返回了 200,服务却报"网络错误"。说明问题不在桩的匹配,而在两端对
**同一条连接的协议理解不一致**。

**第三步:联想 JDK HttpClient 的默认行为。** `java.net.http.HttpClient` 默认
`Version.HTTP_2`;对明文 `http://` 地址,它会在第一个请求上带 `Connection: Upgrade, HTTP2-Settings`
和 `Upgrade: h2c`,尝试升级到 HTTP/2 明文(h2c)。WireMock 3.x 底层是 Jetty,支持 h2c。

**第四步:最小复现,把变量拆开。** 用一个 40 行的单文件 Java 程序,两个变量各两档:

- HTTP 版本:JDK 默认(尝试 h2c)/ 强制 `HTTP_1_1`
- 请求体发送方式:`BodyPublishers.ofString`(带 `Content-Length`)/ `BodyPublishers.ofInputStream`
  (无长度 → `Transfer-Encoding: chunked`,**这正是 Spring `JdkClientHttpRequest` 发 body 的方式**)

每档连发 2 次。结果(2026-09-20 12:19,WireMock 3.9.1):

| 版本 | 请求体 | 第 1 次 | 第 2 次 | WireMock 收到的头 | WireMock 收到的 body |
|---|---|---|---|---|---|
| 默认 | ofString | 200 SPAM | 200 SPAM | `Upgrade: h2c`,`Content-Length: 46` | 完整 |
| **默认** | **ofInputStream** | **`EOF reached while reading`** | **`Received RST_STREAM: Stream cancelled`** | `Upgrade: h2c`,`Transfer-Encoding: chunked` | **空** |
| HTTP/1.1 | ofString | 200 SPAM | 200 SPAM | 无 Upgrade,`Content-Length: 46` | 完整 |
| HTTP/1.1 | ofInputStream | 200 SPAM | 200 SPAM | 无 Upgrade,`Transfer-Encoding: chunked` | 完整 |

只有"h2c 升级请求头 + chunked 请求体"这一格失败,而且两条错误信息和服务日志**一字不差**。
带 `Content-Length` 时 Jetty 直接忽略升级请求、按 HTTP/1.1 处理;chunked 时它接受了升级,
但升级过程中请求体丢失(WireMock 侧 body 为空),客户端等响应时连接被关(EOF),
连接复用后的第二个请求在已升级的 HTTP/2 连接上被 `RST_STREAM`。

## 4. 根因

三个条件同时成立才触发:

1. JDK `HttpClient` 默认 `Version.HTTP_2`,对明文地址发 `Upgrade: h2c`;
2. Spring `JdkClientHttpRequestFactory` 用流式 body publisher,请求是 `Transfer-Encoding: chunked`、没有 `Content-Length`;
3. 对端(WireMock / Jetty)接受 h2c 升级,但对"带 chunked 请求体的升级请求"处理有缺陷,
   请求体被丢弃、连接被切。

任何一个条件不成立都不会触发:直接用 JDK HttpClient + `ofString`(条件 2 不成立)正常;
真实 LLM 供应商走 `https://`(TLS 上用 ALPN 协商,不走 h2c 升级,条件 1 的路径不同)正常。
所以这是一个**只在"Spring RestClient + JDK HttpClient + 明文 HTTP 挡板"这个组合里出现**的问题,
线上真实调用不受影响——但接口自动化默认走挡板,等于整个测试体系的 LLM 路径全部失效。

## 5. 修复

`LlmClientConfig.requestFactory()`:

```java
HttpClient httpClient = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_1_1)     // ← 加这一行
        .connectTimeout(Duration.ofMillis(Math.min(timeoutMs, 2000)))
        .build();
```

真实供应商和挡板共用这个工厂,统一 HTTP/1.1。LLM 调用是一问一答、几十字节,HTTP/2 的
多路复用没有收益,没有理由保留。

修复后重跑同一批用例(04:08):

```
[[SLOW] -> timeout -> rules]  POST /api/tickets -> HTTP 201  3058ms   ← 真的等了 3 秒
[[BAD_CATEGORY] -> OTHER]     POST /api/tickets -> HTTP 201    47ms   category=OTHER
[[BAD_JSON] -> rules]         POST /api/tickets -> HTTP 201    75ms   category=TECH
```

`llm_call_log` 里基线三条变成 `degraded=0`、`response_model=mock-classifier-v1`;
`[BAD_CATEGORY]` 那条 `raw_category=SPAM`、`final_category=OTHER`、`contract_violated=1`。

## 6. 这件事暴露了什么

**1. 降级路径是双刃剑:它让系统在上游坏掉时还能给出"合理"的答案,也让上游坏掉这件事本身
变得不可见。** 五次调用全失败、熔断器都打开了,HTTP 层面零错误、分类结果全部"正确"。
如果没有 `llm_call_log` 和 `llm_fallback_total`,这个问题会一直活到上线——而且线上真实调用
根本不会触发它,只有走挡板的测试环境会,等于 CI 里所有 LLM 用例都在测关键词规则而不是 LLM 路径。

**2. "输出不确定的依赖"的测试断言必须包含"这次到底是谁回答的"。** walkthrough 第 10 节说
LLM 路径只能断言契约(在枚举内),这一条经此事要补一句:**还必须断言 `degraded=false`
和 `response_model` 非空**,否则"契约满足"可能只是规则兜底的副产品。修复后的
`smoke_api.py` 已经把 `degraded` 和 `degradeReason` 纳入断言(回复草稿用例),
下一阶段的 pytest 用例要把它作为 LLM 路径用例的固定断言项。

**3. 每次调用落盘不是"可观测性的锦上添花",是发现这类问题的唯一手段。**
接口响应看不出、HTTP 状态看不出、连日志都要按 WARN 级别去翻;真正一眼定位的是
`SELECT degraded, degrade_reason FROM llm_call_log`。CLAUDE.md §5.5 要求"每次调用落盘"
的价值在这里第一次兑现。

**4. 降级指标应该有告警语义,而不只是仪表盘上的一条线。** `llm_fallback_total` 在服务启动
后 1 秒内从 0 涨到 5、`llm_circuit_state` 变 1——这在生产环境里应该是一条告警。本项目不做
告警(Grafana 看板不在仓库内),但看板上第一个面板应该是降级率而不是 QPS。

**5. "挡板只是换个 URL"是错觉。** 挡板和真实供应商在传输层上就不一样(明文 vs TLS、
Jetty vs 供应商网关),同一套客户端代码在两种传输上可以有完全不同的行为。
ADR-009 决定挡板用独立实现类是对的,但"共用 `requestFactory`"这个设计恰好让挡板暴露了
一个真实调用里看不到的客户端缺陷——这算意外收益,也说明挡板环境的传输层特征应该在
测试设计里被当作一个独立变量。

**6. 排查方法论:两端各取证据、找矛盾点。** 服务说"网络错误",挡板说"我返回了 200"——
矛盾本身就是线索(协议层不一致),然后用最小复现把变量拆开(2×2 四格),让根因不靠推测。
复现程序 40 行,跑一次 2 秒,比在服务日志里猜快得多。

## 7. 复现代码

`H2cRepro.java`(单文件,`java H2cRepro.java` 直接跑,需要 WireMock 在 8089 端口):

```java
import java.io.ByteArrayInputStream;
import java.net.URI;
import java.net.http.*;
import java.nio.charset.StandardCharsets;

public class H2cRepro {
    public static void main(String[] args) throws Exception {
        String body = "{\"title\":\"[BAD_CATEGORY] repro\",\"content\":\"x\"}";
        for (String ver : new String[]{"default", "http1.1"}) {
            for (String pub : new String[]{"ofString", "ofInputStream"}) {
                HttpClient.Builder b = HttpClient.newBuilder();
                if (ver.equals("http1.1")) b.version(HttpClient.Version.HTTP_1_1);
                HttpClient client = b.build();
                for (int i = 1; i <= 2; i++) {
                    HttpRequest.BodyPublisher p = pub.equals("ofString")
                            ? HttpRequest.BodyPublishers.ofString(body)
                            : HttpRequest.BodyPublishers.ofInputStream(
                                    () -> new ByteArrayInputStream(body.getBytes(StandardCharsets.UTF_8)));
                    HttpRequest req = HttpRequest.newBuilder(URI.create("http://127.0.0.1:8089/mock/llm/classify"))
                            .header("Content-Type", "application/json").POST(p).build();
                    try {
                        HttpResponse<String> r = client.send(req, HttpResponse.BodyHandlers.ofString());
                        System.out.println(ver + "/" + pub + "#" + i + " -> " + r.statusCode() + " " + r.body());
                    } catch (Exception e) {
                        System.out.println(ver + "/" + pub + "#" + i + " -> EXCEPTION " + e);
                    }
                }
            }
        }
    }
}
```

跑完后 `GET http://127.0.0.1:8089/__admin/requests` 能看到每个请求的 `Upgrade` /
`Transfer-Encoding` 头和 WireMock 实际收到的 body。

# 附:同一轮联调修掉的另外四个问题(简记)

## A. 3 秒超时被记成 `UPSTREAM_ERROR` 而不是 `TIMEOUT`

- **现象**:h2c 修复后,`[SLOW]` 用例耗时 3012ms、`degraded=true`,但 `degradeReason=UPSTREAM_ERROR`;
  服务日志 `msg=LLM 网络错误: TimeoutException`。
- **根因**:`LlmHttpSupport.isTimeout()` 只识别 `java.net.http.HttpTimeoutException` 和
  `SocketTimeoutException`;而 Spring `JdkClientHttpRequest` 实现 `readTimeout` 的方式是
  `sendAsync(...).get(timeout)`,超时抛的是 `java.util.concurrent.TimeoutException`,包在 `IOException` 里。
- **修复**:异常链遍历时加上 `TimeoutException`。
- **教训**:超时的"异常类型"取决于中间有几层框架,不能只按 JDK 文档写;降级原因的枚举
  必须用挡板逐个触发验证,不能只验"降级了"。

## B. `updated_at` 永远等于创建时间

- **现象**:一张工单流转五次,`updatedAt` 仍是 `04:06:59`(创建时刻),`closedAt` 是 `04:07:03`。
- **根因**:`MetaObjectHandler.updateFill` 用了 `strictUpdateFill`,它**只在字段为 null 时填**;
  `updateById` 传入的实体是从库里查出来的,`updatedAt` 已有值,所以从不覆盖。
- **修复**:`updateFill` 改用 `setFieldValByName("updatedAt", now, metaObject)` 无条件覆盖。
- **教训**:MyBatis-Plus 的 `strict*Fill` 语义是"补空"不是"覆盖",对 `updated_at` 这种
  必须每次变化的列是错的;而且这个 bug 在只看接口状态码的测试里永远发现不了,
  要靠断言 `updatedAt != createdAt`(已加进 `smoke_api.py`)。

## C. 坐席中文名双重编码

- **现象**:`GET /api/agents/me` 返回 `displayName: "åå¸­A"`;数据库里 `HEX(display_name)`
  是 `C3A5C29D...`(UTF-8 字节被当 latin1 再编一次)。
- **根因**:MySQL 官方镜像对 `/docker-entrypoint-initdb.d/` 下**每个 SQL 文件开一个独立的
  mysql 客户端会话**;`01-schema.sql` 开头的 `SET NAMES utf8mb4` 对 `02-seed.sql` 无效,
  后者按客户端默认字符集(latin1)发送。
- **修复**:`02-seed.sql` 自己加 `SET NAMES utf8mb4`;`docker compose down -v` 重建数据卷。
  修复后 `HEX(display_name)` = `E7AEA1E79086E59198`(管理员)。
- **教训**:初始化脚本之间没有"会话状态"可以共享,每个文件都要自包含;
  以及冷启动(`down -v`)才能验证初始化脚本,在已初始化的卷上重跑什么都测不到。

## D. Redis 挂掉会让鉴权变 500

- **现象**:设计上缓存只是加速器,但 `@Cacheable` 的默认行为是把 Redis 异常原样抛出——
  `docker compose stop redis` 后 `AgentCache.findSnapshot` 会抛 `RedisConnectionFailureException`,
  所有带 `X-User-Id` 的请求都会 500(这是在写 README 故障注入段落时意识到的,先于实测)。
- **修复**:`CacheConfig` 实现 `CachingConfigurer.errorHandler()`,缓存 get/put/evict 失败
  只打 WARN,当作未命中回源查库;同时 Lettuce 超时从 2s 降到 500ms。
- **实测**(`smoke_faults.py`):Redis 停掉后 `GET /api/agents/me` → 200,耗时 4071ms
  (改 500ms 前;两次缓存操作各等一次超时),`/actuator/health` → 503 且 `redis: DOWN`,
  SLA 扫描 fail-open 继续、`sla_scan_lock_unavailable_total` = 2;Redis 恢复后 12ms。
- **教训**:"缓存不是依赖"是一句设计意图,不是框架默认;必须显式配置错误处理器并用故障注入验证。
  这类"设计上以为如此、实际框架默认相反"的点,靠读代码发现不了,靠停容器才能发现。
