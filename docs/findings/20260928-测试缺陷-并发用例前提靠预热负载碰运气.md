# 2026-09-28 测试缺陷 · 并发用例的前提"池已撑满"在 CI 上靠预热负载碰运气

> 记录类型:测试自身缺陷(不编 KI 号)。决策与完整分析见 [ADR-021 修订 #1](../adr/ADR-021-压测结果可复现-连接池预热与并发断言写法.md)。
> 数据来自 GitHub Actions 运行记录、CI 上传的 Allure 原始结果与服务日志,以及本地复现。

## 1. 现象

CI run 36433276730(main 52eafb2),接口自动化一步:

```
ERROR at setup of TestGrabRace.test_only_one_wins[t2]
E       AssertionError: 连接池未撑满: total=18.0 max=20.0
E       assert (20.0 == 0 or 18.0 >= 20.0)
```

7 条并发用例在 `warmed_pool` fixture 的前置断言上 error(6 条 18/20、1 条 19/20),用例本身没有执行。
同一报错此前出现在 run 35632413645(096ac19,19/20)与 v0.5 的 run 36308296066(19/20)。

## 2. 根因

池的大小由负载"同时让多少线程排队等连接"决定,不由压多久决定;runner 上的 Python 负载源够不到 20。

- HikariCP 5.1.0 只在有线程等连接时补连接(`addBagItem`;`PoolEntryCreator.shouldContinueCreating` 要求 `idle < minimumIdle` 或 `waitingThreadCount > idle`),
  默认 `minimum-idle: 2` 下 HouseKeeper 只补到 2。
- CI:`tools/warm_pool.py`(25 线程持续创建 3 × 2 s)结束时 16/20;随后 7 次 fixture 预热合计约 75 s 同样的负载,池只从 16 涨到 19;
  服务端这段时间 70~210 条/s,`TicketMapper.insert` p50 2 ms。——"请求太快、还没来得及建连接就结束"已由上一版预热(持续 2 s)解决,
  这次持续压了 75 s 仍不满,排除了"时间不够"。
- 本地复现(冷启动服务、默认配置、每 0.1 s 采 `hikaricp_connections`):6 线程持续 10 s,池 2 → 8 后 9 s 不变;
  12 线程持续 10 s,池到 12 后 6 s 不变。池停在负载能制造的排队深度上。本机 25 线程(260 条/s)能到 20,所以本地一直没暴露;
  runner 上吞吐更低的原因(CPU 被 JVM / MySQL / RabbitMQ / WireMock / Python 负载源分掉)是推断。
- ADR-021 原决定写的"持续打让'有人在等'贯穿整个建连过程,快慢机器都在一轮内到上限"被这次的数据推翻;ADR-023 在容量用例上得出过同样的结论。

## 3. 修复(前置断言不改)

- `application.yml`:`minimum-idle: ${HIKARI_MINIMUM_IDLE:2}`,默认值不变。
- CI「起服务(后台)并等待 health UP」一步设 `HIKARI_MINIMUM_IDLE=20`:Hikari 启动后自己补满 20 条,"池已满"由环境构造;
  容量用例那一步用小池重启时不带这个变量(ADR-023 不变)。
- `start-service.sh` 启动后打印 `hikaricp_connections` / `_max` / `_min`,每次 CI 都留下"起跑时池是多少"的证据。
- `warm_pool.py`、`warmed_pool` fixture 与断言 `total >= max` 保持原样;CI 上它们变成确认。

## 4. 验证

本地按 CI 的方式连跑 3 次:每次停服务 → `HIKARI_MINIMUM_IDLE=20` 起服务 → `coverage run tools/warm_pool.py` →
`coverage run --append -m pytest -m "not capacity" --alluredir=allure-results -p no:cacheprovider`(CI「接口自动化 + 安全用例」一步的同一命令)。

| 次 | 起服务后 `hikaricp_connections` / `_max` / `_min` | `warm_pool.py` | pytest -m "not capacity" | 并发用例 |
|---|---|---|---|---|
| 1(23:09–23:14) | 20 / 20 / 20 | 20/20 | 316 passed、3 xfailed、0 failed / error(5 分 25 秒) | 8 passed |
| 2(23:14–23:20) | 20 / 20 / 20 | 20/20 | 316 passed、3 xfailed、0 failed / error(5 分 35 秒) | 8 passed |
| 3(23:20–23:26) | 20 / 20 / 20 | 20/20 | 316 passed、3 xfailed、0 failed / error(5 分 27 秒) | 8 passed |

第 3 次的 Redis 停机用例走的是 timed out 路径(`/me` 1029 / 1021 / 1022 ms)。

**作废的一批(如实记录)**:这三次之前的一批(22:51–23:08)三次都是 1 failed:`test_audit_chain.py::test_no_broken_chain_in_database`
报工单 49876 "没有任何审计行"。这张工单创建于 22:50:56,正是执行者(Claude)为修本地运行脚本的健康检查而强行结束上一次运行的时刻——
fixture 的清理按"先删审计、最后删工单"逐表执行,进程在两者之间被杀,留下一张没有审计的工单。它是本地操作留下的残留数据,
不是服务或用例的问题;全库只有这一张,硬删后重新连跑 3 次(上表)。
CI 每次都是全新数据库,不受影响。
