# 压测记录:审计日志记录了未发生的状态转换(问题 B · 观测手段失效)

> 2026-09-20 实测。与[抢单并发重复分配](20260920-压测-抢单并发重复分配.md)来自同一批压测,但**故意分开记**:
> A 是数据错了(业务缺陷),B 是用来发现 A 的工具也错了(观测手段失效)。两者修法不同、影响面不同。
> 原始文件在本机 `tests/perf/results/`(gitignore 不入库);文中引用到的关键证据已复制到 [`docs/findings/evidence/20260920/`](evidence/20260920/)(同名文件)。

## 1. 现象

同一张工单在 `ticket_audit_log` 里出现 N 条 `from_status='PENDING', to_status='ASSIGNED'`,但库里的状态只从 PENDING 变成过 ASSIGNED **一次**。后面 N-1 次 UPDATE 执行时,行上已经是 ASSIGNED——真实发生的转换是 `ASSIGNED→ASSIGNED`(换人),审计却记成 `PENDING→ASSIGNED`。

最清楚的一次是持锁演示(ticket 8241,`results/lockhold_*`):

```
18:44:08.318  组长会话  UPDATE ticket SET assignee_id=2, status='ASSIGNED' WHERE id=8241   (BEGIN 后持锁 45 s)
18:44:11      5 个 grab 请求 SELECT → 读到 PENDING → 在 UPDATE 上等行锁
18:44:53.327  组长 COMMIT                     ← 此后库里的状态是 ASSIGNED, assignee=2
18:44:53.536  审计#10907  PENDING→ASSIGNED  operator=3   ← 库里已是 ASSIGNED 42.8 s 了
18:44:53.541  审计#10908  PENDING→ASSIGNED  operator=4
18:44:53.548  审计#10909  PENDING→ASSIGNED  operator=3
18:44:53.556  审计#10910  PENDING→ASSIGNED  operator=4
18:44:53.564  审计#10911  PENDING→ASSIGNED  operator=3
```
5 条审计的 `from_status` 都是 42 s 前的旧值。组长那次指派(assignee 2)在审计里连一行都没有——它不走 grab,而 grab 的 5 条又都说"从 PENDING 来的",于是审计表里根本看不出组长指派过、也看不出它被覆盖了。

## 2. 产生路径(脏读的来源是内存快照,不是数据库)

```
TicketService.grab
  216  Ticket ticket = getOrThrow(id);                        // SELECT,得到一个内存对象,status=PENDING
  218  if (ticket.getStatus() != PENDING) throw ...;          // 用内存对象判断
  223  TicketStatus from = stateMachine.transit(ticket, ASSIGNED, now);
        └─ TicketStateMachine.transit 第 43 行  TicketStatus from = ticket.getStatus();   // ← from 取自内存对象
  224  ticketMapper.updateById(ticket);                        // 这里才拿行锁;等锁期间库里可能已被别人改
  226  auditLogService.record(id, from, ASSIGNED, ...);        // 写进去的 from 仍是 SELECT 时刻的快照
```

`from_status` 在 SELECT 时刻就定了,UPDATE 等锁多久、期间行被改成什么,都不会反映进来。MySQL 的 REPEATABLE-READ 保证了"这个事务内看到的是一致快照",这恰好意味着它**看不到**别的事务刚提交的 ASSIGNED。所以这不是 MySQL 的脏读(隔离级别没问题),是应用层把"读时刻的状态"当成了"写时刻的状态"。

## 3. 影响

- **审计失去追溯可信度。** 审计表的用途(CLAUDE.md §5.8)是"数据一致性校验":从审计能还原状态历史。现在它还原出来的历史是 `PENDING→ASSIGNED` 发生了 12 次,而真实历史是 1 次 `PENDING→ASSIGNED` + 11 次 `ASSIGNED→ASSIGNED`。
- **它把问题 A 藏起来了。** 如果只看审计,会以为工单被"正常"分配了 12 次(每次都合法地从 PENDING 出发),而不是被覆盖了 11 次。取证阶段真正暴露问题的是"同一 ticket_id 多条 to_status=ASSIGNED"这个计数,不是 from/to 本身——from/to 在撒谎。
- 状态迁移表校验(`docs/test-design` 里的状态迁移法)如果拿审计表做事后校验,会全部通过:每一行 `PENDING→ASSIGNED` 都是合法迁移。校验器被喂了假数据。
- 范围不止 grab:`transit()`、`assign()`、`escalate` 都是"SELECT → 内存判断 → UPDATE → 用内存里的 from 写审计",凡是两个写者撞上同一行,都会写出不存在的转换。压测只在 grab 上验证了。

## 4. 与问题 A 的区别

| | A 重复分配 | B 审计脏 from_status |
|---|---|---|
| 性质 | 业务缺陷:数据最终是错的 | 观测缺陷:数据可能对也可能错,但记录它的手段不可信 |
| 谁受害 | 坐席 / 客户(一张单被多人处理、通知发多份) | 排障的人、审计校验、事后回放 |
| 修 A 之后 B 还在吗 | 修 A(条件 UPDATE / 乐观锁)后,失败的写者不再落审计,B 在 grab 上**自然消失**;但 `assign()` 的 `ASSIGNED→ASSIGNED` 改派、以及未来任何"读-判断-写"路径,B 的成因仍在 | — |
| 单独的修法 | — | 让 `from_status` 来自写时刻:① 条件 UPDATE 成功后才记审计,`from` 就是 WHERE 里断言的那个值,天然一致;② 或在 UPDATE 后 `SELECT ... FOR UPDATE` 回读;③ 或审计表加 `expected_from` / `actual_from` 两列并在校验器里比对 |

## 6. 修复建议(只写不做)

优先级低于 A,但建议同一次修:把"判断"下沉到 UPDATE 的 WHERE 里之后,审计的 `from` 直接用 WHERE 里的期望值,两个问题一次消掉。另建议给 `docs/test-design` 的状态迁移校验补一条**反向断言**:同一 ticket_id 的审计序列必须首尾相接(第 k 行的 to_status == 第 k+1 行的 from_status),这条断言在今天的数据上会失败——它是能发现 B 的最便宜的检查。
