# 2026-09-26 · 测试自身缺陷:SLA 升级用例混用了两个时钟

> 类型:**测试缺陷,不是产品缺陷**。SLA 扫描的判定(`sla_deadline <= now`,闭区间,ADR-006)没有错;是用例构造"已超时"时用的时钟和服务判定时用的时钟不是同一个。
> 记录方式:本仓库只写真实跑出来的结果;下面每一行都来自本机 2026-09-26 的运行,运行记录的原文照抄在 §4。

## 1. 现象

`tests/api/test_sla.py::TestEscalation` 的 3 条用例在本机时好时坏:

- `test_overdue_pending_is_escalated`、`test_overdue_assigned_is_escalated`:把截止时间设成"1 秒前"、调扫描接口,期望工单变成 ESCALATED,实际仍是 PENDING / ASSIGNED;
- `test_deadline_in_near_future`:截止时间设成"3 秒后",睡 3.5 秒再扫,期望 ESCALATED,实际仍是 PENDING。

2026-09-26 注入任务 v1 前的全量回归里 3 条都失败,单独重跑仍失败(findings/20260926-LLM提示词注入-防御后复测 §7)。

## 2. 根因

两个时间来自两台"机器":

| 值 | 谁的时钟 |
|---|---|
| 用例写进库的截止时间 `NOW(3) - 1s`(`db.set_sla_deadline_now`) | MySQL 容器,跑在 WSL2 虚拟机里 |
| 扫描拿来比较的 `now`(`SlaScanner`:`LocalDateTime.now(clock)` → `sla_deadline <= #{now}`) | 服务进程,跑在 Windows 宿主上 |

WSL 虚拟机的时钟比宿主快超过 1 秒时,"数据库的 1 秒前"在服务看来还是"将来",扫描不命中。
`set_sla_deadline_now` 的注释写的是"用 DB 时钟避免宿主与容器时钟不一致"——它只保证了**用例自己**只用一个时钟,没有注意到判定方(服务)用的是另一个。

本机实测的时钟差(`SELECT NOW(3)` 对宿主时间,三次取中位数)在几十秒到几分钟内在 **−1.1 s 到 +1.7 s** 之间来回摆动(见 §4 每行的 `db-host`),
不是一个固定偏差——这就是它"时好时坏"的原因:差值恰好大于 1 s 的那几分钟里跑,就失败。

## 3. 修法:只用数据库里服务写下的时间

新 helper `db.set_sla_deadline_from_last_write(ticket_id, offset_seconds)`:
`UPDATE ticket SET sla_deadline = TIMESTAMPADD(MICROSECOND, offset, updated_at)`。
`updated_at` 是服务每次写工单时用**自己的时钟**写进库的,用它做基准,截止时间和扫描的 `now` 就出自同一个时钟;库里的 `NOW(3)` 与宿主时间都不再参与。
剩下的前提只有"服务的时钟不倒退"。`TestEscalation` 的 5 处构造全部改用它(含"已响应不升级"的 −60 s);`test_deadline_in_near_future` 仍是"+3 s 不命中、睡 3.5 s 后命中",
两个判断都只涉及服务时钟上的时间差。断言一条没改。

**为什么不改服务**(例如扫描改用 `NOW()`):产品的时间来源是服务的 `Clock`(注入、可在单测里固定,ADR-006 的边界值单测靠它),为了测试环境的时钟差去改产品是本末倒置。
