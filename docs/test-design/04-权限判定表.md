# 04 · 权限判定表

方法:**判定表法**。

为什么用判定表:权限规则是"角色 × 是否同组 × 是否分配给自己 → 放行 / 40301 / 40302"的组合,
而且两种拒绝码有语义差别(40301 身份不对 = 水平越权,40302 角色不够 = 垂直越权)。
判定表让"看起来像能过"的格子——同组别人的单、跨组的组长、ADMIN 抢单——都被显式列出来,
而不是只测"自己的单能过、别人的单不能过"两条。

规格(CLAUDE.md §5.6):AGENT 只能读写分配给自己的;LEADER 本组全部可读可写、可改派;ADMIN 全权。
校验在 Service 层(ADR-007),所以每个带 `{id}` 的接口都要过一遍表,不能只测一个。

## 1. 读 / 写(`checkRead` / `checkWrite`,同一套规则)

条件:C1 角色;C2 工单是否本组;C3 工单是否分配给自己。

| # | C1 角色 | C2 本组 | C3 分配给自己 | 动作 | 单测(`AccessCheckerTest.readWriteTable`) | 接口 |
|---|---|---|---|---|---|---|
| 1 | AGENT | 是 | 是 | 放行 | agent_a 读自己的单 | `test_owner_leader_admin_allowed` |
| 2 | AGENT | 是 | 否(别人的) | **40301** | agent_b 读同组别人的单 | `test_every_endpoint_rejects_non_owner[agent_b]` |
| 3 | AGENT | 是 | 否(PENDING 无人) | **40301** | agent_a 读同组 PENDING 单 | `test_pending_ticket_visibility` |
| 4 | AGENT | 否 | 否 | 40301 | agent_c 读跨组的单 | `…[agent_c]` |
| 5 | LEADER | 是 | — | 放行 | leader_1 读本组任意单 / PENDING 单 | `test_owner_leader_admin_allowed` |
| 6 | LEADER | 否 | — | **40301** | leader_2 读跨组的单 | `…[leader_2]`、`test_cross_group_leader` |
| 7 | ADMIN | — | — | 放行 | admin 读任意组 | `test_owner_leader_admin_allowed` |

第 3 行是容易漏的:PENDING 单没有 assignee,AGENT 对它**没有读权限**,但**有抢单权限**(见 §2)——
"能抢"和"能看"是两套规则。

接口层把这张表对每一个带 id 的接口各打一遍(`ENDPOINTS × INTRUDERS` = 7 × 3 = 21 条参数化,
`test_horizontal_privilege.py`),并断言越权尝试没有副作用(状态、assignee、标题、审计条数、附件都不变)。

## 2. 抢单(`checkGrab`:同组即可,不看 assignee)

| # | 角色 | 本组 | 动作 | 用例 |
|---|---|---|---|---|
| 1 | AGENT | 是 | 放行 | `grabTable[agent_a/agent_b]`;接口 `test_grab_pending` |
| 2 | AGENT | 否 | 40301 | `grabTable[agent_c]`;接口 `test_grab_across_group[agent_c]` |
| 3 | LEADER | 否 | 40301 | `grabTable[leader_2]`;接口 `test_grab_across_group[leader_2]` |
| 4 | LEADER | 是 | 放行 | 接口 `test_leader_and_admin_can_grab` |
| 5 | ADMIN | — | 放行 | `grabTable[admin]`;接口同上 |

状态不是 PENDING 时的拒绝(409)属于状态机,见 01。

## 3. 指派 / 改派(`checkAssign`:先查角色,再查组)

| # | 角色 | 本组 | 动作 | 说明 | 用例 |
|---|---|---|---|---|---|
| 1 | AGENT | 是(自己的单) | **40302** | 角色不够,哪怕改给自己 | `assignTable[agent_a]`;接口 `test_agent_cannot_assign_even_own_ticket` |
| 2 | AGENT | 是(同组别人的) | 40302 | | `assignTable[agent_b]` |
| 3 | LEADER | 是 | 放行 | | `assignTable[leader_1]`;接口 `test_leader_assigns_pending`、`test_leader_reassigns` |
| 4 | LEADER | 否 | **40301** | 角色够,组不对 | `assignTable[leader_2]`;接口 `test_leader_scope`、`test_cross_group_leader` |
| 5 | ADMIN | — | 放行 | | `assignTable[admin]`;接口 `test_admin_assigns_any_group` |

检查顺序决定错误码:`checkAssign` 先 `requireRole`(40302)再比组(40301)。
但 `transit(target=ASSIGNED)` 走的顺序是 `checkWrite`(40301)→ `checkAssign`(40302),所以:

| 场景 | 先撞到哪个检查 | 结果 | 用例 |
|---|---|---|---|
| AGENT 对自己的 ESCALATED 单 transit 到 ASSIGNED | checkWrite 过(是自己的)→ checkAssign 角色不够 | 40302 | `test_agent_cannot_assign_via_transitions`、单测 `agentTransitionToAssignedIsVerticalEscalation` |
| AGENT 对 PENDING 单 transit 到 ASSIGNED | checkWrite 不过(没分配给自己) | 40301 | `test_check_order_on_pending` |

这两条一起证明"绕开 assign 接口、用 transitions 接口把目标写成 ASSIGNED"绕不过校验——因为校验在 Service 层,不在 Controller。

## 4. 只有 ADMIN 的操作(`requireRole(ADMIN)`)

| 操作 | AGENT | LEADER | ADMIN | 用例 |
|---|---|---|---|---|
| DELETE 工单 | 40302 | 40302 | 放行(逻辑删) | `test_delete_requires_admin`(3 个角色参数化)、`test_delete_is_logical` |
| POST /api/admin/sla/scan | 40302 | 40302 | 放行 | `test_sla_scan_requires_admin`、`test_scan_permission` |

## 5. 列表接口的收窄(不是拒绝,是过滤)

列表不返回 403,而是按角色自动加条件:AGENT `assignee_id = me`,LEADER `group_id = my group`,ADMIN 无条件。
判定:结果集里每一条都满足条件,且已知的"别人的单"不在里面(`test_agent_sees_own_only`、`test_leader_sees_group`、
`test_admin_sees_all_with_filter`、`test_list_does_not_leak`)。`status` 过滤参数不能扩大范围。

## 6. 认证(不是授权)的等价类

`X-User-Id` 的输入域:缺失 / 空白 / 非数字(`abc`、`1e3`、`0x3`、`3.0`)/ 逗号多值 / 不存在(999)/ 负数 / 0 / 存在。
除"存在"外全部 401 / 40101(`test_invalid_header_values`、`test_unknown_user`、`test_user_id_header_tricks`);
6 个种子坐席各自返回正确的角色和组(`test_seed_users`)。
角色不能通过 body / query / 额外头伪造(`test_role_cannot_be_injected`)。
