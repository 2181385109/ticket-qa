# 06 · MQ 幂等与审计一致性——场景法

方法:**场景法**。

为什么用场景法:异步链路没有"输入 → 输出"的函数形状,它是一串事件——状态变更、事务提交、消息发出、消费者收到、
去重表插入、业务执行——每一步都可能重复或失败。按"主路径 + 每个备选分支"组织成场景,
一条场景对应一次完整的链路走法,比孤立地测一个方法更能说明幂等性成立。

规格(CLAUDE.md §5.4、ADR-003):三类事件走 RabbitMQ;消费端幂等靠 MySQL 去重表 `(message_id, consumer)` 唯一键,
去重记录与业务在同一本地事务。

## 1. 生产端

| 场景 | 期望 | 用例 |
|---|---|---|
| P1 事件类型 → 路由键 | STATUS_CHANGED→`ticket.status.changed`、SLA_ESCALATED→`ticket.sla.escalated`、ASSIGNED→`ticket.assigned` | `TicketEventPublisherTest.routingKeys` |
| P2 字段映射 | 消息体 12 个字段与领域事件一一对应,messageId 是 UUID | `routesByEventTypeAndMapsFields` |
| P3 messageId 每次唯一 | 同一事件发两次 id 不同(去重靠 id 不靠内容) | `messageIdIsUniquePerSend` |
| P4 Broker 不可用 | 不抛(事务已提交),`mq_event_publish_failed_total`+1,`published` 不增 | `brokerDownIsCountedNotThrown` |
| P5 抢单发两条 | STATUS_CHANGED + ASSIGNED,各自消费者各一行,id 互不相同,`published/consumed` 各 ≥3(含创建) | 接口 `test_grab_publishes_two_events` |
| P6 非法流转不发 | 409 之后去重表无新增 | 接口 `test_illegal_transition_publishes_nothing` |
| P7 SLA 升级发两条 | SLA_ESCALATED(sla-escalated-notifier)+ STATUS_CHANGED(status-changed-notifier) | 接口 `test_escalation_publishes_two_events` |
| P8 traceId 跨线程 | 消费记录的 trace_id == 触发它的 HTTP 请求的 X-Trace-Id | 接口 `test_trace_id_propagates_to_consumer` |

"AFTER_COMMIT 才发送"这条事务语义单测测不到(Mock 里没有事务),由 P5 / P7 间接证明:去重表里出现记录时,工单的新状态已经在库里。

## 2. 消费端幂等

单测用 Mockito 模拟唯一键(同一 `(messageId, consumer)` 第二次 insert 抛 `DuplicateKeyException`),
H2 切片证明真实唯一键抛的确实是这个异常类型(`MqMessageDedupH2Test`),接口层用 RabbitMQ 管理 API 真实重投。

| 场景 | 步骤 | 期望 | 单测(`IdempotentConsumerSupportTest`) | 接口(`test_mq_idempotency.py`) |
|---|---|---|---|---|
| C1 首次消费 | insert 成功 → 业务执行 | 去重行字段完整;`consumed`+1 | `firstConsumptionWritesFullDedupRow` | — |
| **C2 同一消息投递两次** | 第二次 insert 唯一键冲突 | 业务只执行一次;`duplicate`+1;不抛异常(消息正常 ack) | `sameMessageDeliveredTwiceRunsBusinessOnce`、`duplicateIsSilentlySkipped` | `test_redelivery_is_deduplicated`(去重表不增、consumed 不增、duplicate+1) |
| C3 同一消息、不同消费者 | 唯一键含 consumer | 各处理一次 | `sameMessageDifferentConsumersEachRunOnce` | `test_same_id_different_consumers`(用 ASSIGNED 的 id 发到 status-changed 队列) |
| C4 内容相同、id 不同 | 新 id | 视为新消息,去重表 +1 | (P3) | `test_new_message_id_is_processed` |
| C5 业务抛异常 | insert 成功、业务失败 | 异常向上传播(事务回滚,去重行一起消失,重投后可再处理);`consumed` 不计 | `businessFailurePropagatesAndDoesNotCount` | — |
| C6 traceId 进 MDC | | 业务里能读到消息的 traceId;结束后 MDC 清空;缺失时用 `mq-<messageId>` 兜底 | `traceIdPropagatedToMdcAndCleared`、`missingTraceIdFallsBackToMessageId` | (P8) |
| C7 队列不积压 | | 三个队列消费后深度为 0 | — | `test_queues_drain` |
| C8 三个消费者各用自己的名字 | | consumeOnce 的 consumer 参数分别为三个固定名 | `consumersUseTheirOwnNames` | — |

C5 是"为什么用 MySQL 表而不是 Redis setnx"的直接证据:去重记录和业务在同一事务,业务失败去重记录一起回滚;
setnx 做不到这一点,会出现"标记已处理、业务没做、消息不再重投"的窗口(ADR-003)。

## 3. 审计一致性(CLAUDE.md §5.8:用于数据一致性校验)

| 场景 | 期望 | 用例 |
|---|---|---|
| A1 创建 | 恰好一条,from=null,to=PENDING,source=LLM,备注含分类结果(含 degraded / contractViolated 标记),traceId 与请求一致 | `test_initial_audit_log`、单测 `PersistenceHelpersTest.auditRecordFillsTraceId` |
| A2 每次合法流转 | 恰好一条,from/to 与响应一致,operator_id 与请求方一致,source=MANUAL,trace_id == X-Trace-Id | `test_audit_matches_every_transition`(4 步各带独立 traceId) |
