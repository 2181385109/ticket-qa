# ADR-013: 单测按被测对象分三种替身——Mockito、进程内 MockRestServiceServer、H2 切片;不用 Testcontainers 和进程内 WireMock

## 背景

CLAUDE.md §3 单测锁定 JUnit 5 + Mockito,任务要求"Mock 掉 DB 和外部依赖"。
但有两处语义 Mockito 碰不到:

1. SLA 闭区间"恰好等于时限即超时"落在 `TicketMapper.selectSlaOverdueIds` 的 SQL `sla_deadline <= #{now}` 上,
   `<=` 和 `<` 的差别是 SQL 的事,Mock 掉 Mapper 就把被测物 Mock 掉了。
2. MQ 幂等靠去重表唯一键抛 `DuplicateKeyException`,`IdempotentConsumerSupport` 只 catch 这一种异常;
   唯一键冲突到底翻译成哪个异常类型,是 Spring 异常翻译 + 数据库驱动共同决定的,Mock 里是我写的。

另外 `WireMockLlmClient` 的"请求怎么发、响应怎么解析"是 HTTP 层逻辑,Mock `RestClient` 会把 JSON 解析一起 Mock 掉。

## 选项

- **方案 A:全部 Mockito**
  做法:Mapper、RestClient 全 Mock。
  代价:上面两处语义测不到,只能"相信 SQL 写对了";`WireMockLlmClientTest` 会退化成测 Mock。

- **方案 B:Testcontainers 起真 MySQL / WireMock / RabbitMQ 跑集成测试**
  做法:`@SpringBootTest` + 容器。
  代价:单测从秒级变分钟级;本机没有 Docker Desktop(WSL 里的 Docker 对 Testcontainers 要额外配 socket);
  CI 要拉三个镜像。而且这些链路接口自动化已经对着真容器测了,单测层再起一遍是重复投入。

- **方案 C:进程内 WireMock(`wiremock` 的 JUnit 扩展)测 LlmClient**
  做法:测试里起一个嵌入式 WireMock,LlmClient 真的走 HTTP。
  代价:多一个测试依赖(WireMock 3 带 Jetty 12,和 Spring Boot 3.3 的 Jetty 版本要对齐);
  能测到超时和 h2c 这类传输层问题——但那正是接口自动化对着真容器已经覆盖的,
  单测层只需要"响应体 → ClassifyResult"的解析逻辑。

- **方案 D:按被测对象分三种替身** ← 采用
  | 被测对象 | 替身 | 理由 |
  |---|---|---|
  | Service 编排(权限 → 状态机 → 落库 → 审计 → 事件) | Mockito Mock Mapper / 事件发布器 / LlmService | 被测的是编排顺序和条件,不是 SQL |
  | 状态机、熔断器、规则分类器、AccessChecker、FileTypeSniffer | 不用替身,纯对象 | 没有外部依赖 |
  | `LlmService` 韧性外壳 | Mock `LlmClient`(抛 LlmException 或返回越界值)+ `MutableClock` 拨时间 | 超时 3 秒、熔断 60 秒都靠拨表,不 sleep |
  | `WireMockLlmClient` 的请求组装 / 响应解析 | Spring 自带 `MockRestServiceServer` 绑定 RestClient | 进程内截 HTTP,零新依赖;传输层问题留给接口自动化 |
  | `TicketMapper` 两条手写 SQL、去重表唯一键 | `@MybatisPlusTest` 切片 + 内存 H2(MySQL 兼容模式) | 真 SQL、真唯一键、真异常翻译,启动约 1 秒 |
  | Controller / 拦截器 / ControllerAdvice / 参数校验 | `@WebMvcTest` 切片 + `@MockBean` Service | 只起 MVC 那一层,测 HTTP 边界上的翻译 |

## 决定

方案 D。新增两个 test 依赖:`mybatis-plus-spring-boot3-starter-test`、`h2`。
H2 建表脚本单独维护在 `src/test/resources/h2/schema.sql`,只含 `ticket` 和 `mq_message_dedup` 两张表,
去掉了 `UNSIGNED / COMMENT / ENGINE / CHARSET` 这些 H2 不认或无意义的修饰。

组合注解 `@H2SliceTest` 把 `@MybatisPlusTest + @AutoConfigureTestDatabase(NONE) + @Import(MybatisPlusConfig, 固定 Clock) + H2 属性`
打包成一个,两个切片测试类共用。

## 后果

- 接受了:H2 的 MySQL 兼容模式不是 MySQL。`<=` 的语义、`LIMIT`、`IS NULL`、唯一键冲突这些两边一致,
  但 `DATETIME(3)` 的舍入、隐式类型转换、`NOW(3)` 这类函数可能有差异——所以 H2 切片只跑 Mapper 里
  **参数化**的那两条 SQL,不跑任何带 MySQL 函数的语句;真 MySQL 上的行为由接口自动化里的 SLA 用例覆盖。
- 接受了:`schema.sql` 是 DDL 的第二份拷贝,改表结构要同步;漏改会在切片测试启动时报列不存在,不会静默。
- 接受了:`MockRestServiceServer` 测不到超时、连接复用、h2c 升级——这些恰好是联调时真正出过问题的地方
  (docs/findings/20260920)。所以它们在接口自动化里对着真 WireMock 容器有专门用例(`[SLOW]` 超时、请求体非空)。
- 什么场景下这个选择是错的:如果 Mapper 里开始出现 MySQL 专有 SQL(`ON DUPLICATE KEY UPDATE`、
  窗口函数、JSON 函数),H2 切片会跑不了或跑出假结果,那时应该换 Testcontainers 起真 MySQL。

## 常见质疑与回应

**"任务说 Mock 掉 DB,你为什么起了 H2?"**
> 因为被测的就是 SQL 本身。"恰好等于时限即超时"是 ADR-006 定下的闭区间,它的实现是 `sla_deadline <= #{now}`;
> 把 Mapper Mock 掉,测试里的 `<=` 是我自己写的,等于拿实现测实现。H2 是内存库,一秒起,没有容器、没有网络,
> 对单测来说它和 Mock 一样"不依赖环境",区别只是它真的执行 SQL。除这两条 SQL 和一个唯一键之外,所有 DB 访问都是 Mockito。

**"H2 不是 MySQL,测出来的结果可信吗?"**
> 对这两条语句可信:比较运算、`IN`、`IS NULL`、`ORDER BY`、`LIMIT`、唯一索引冲突,两边语义一致。
> 我刻意不在 H2 上跑任何带 MySQL 函数的语句。真 MySQL 上的行为有接口自动化兜着——`test_sla.py`
> 把截止时间拨到 now-1s 和 now+3s 两侧,在真库上验证扫描结果;两层各测各的,H2 测边界精度,MySQL 测集成。

**"为什么不用 Testcontainers?"**
> 单测要快、要在没有 Docker 的机器上能跑——本机就没有 Docker Desktop。Testcontainers 把单测变成集成测试,
> 每次 `mvn test` 拉容器,CI 也慢一截。而接口自动化已经对着真容器把这些链路跑了一遍,再在单测层起一遍是重复。
> 如果哪天 Mapper 里出现 MySQL 专有 SQL,H2 跑不了了,那时候再上 Testcontainers 是对的,现在不是。

**"为什么不用进程内 WireMock 测 LlmClient?"**
> 因为单测层只需要测"响应 JSON 怎么变成 ClassifyResult、缺字段怎么处理、非 2xx 怎么翻译",
> Spring 自带的 MockRestServiceServer 在进程内截住 RestClient 就够了,零新依赖。
> 进程内 WireMock 能多测到超时和 h2c——但那些是传输层的事,恰好是接口自动化对着真 WireMock 容器
> 已经有专门用例的地方(联调时的 h2c 问题就是在真容器上暴露的,进程内 WireMock 的 Jetty 版本还不一定复现)。

**"@WebMvcTest 和 @SpringBootTest 有什么区别,为什么选前者?"**
> `@SpringBootTest` 起整个容器,要连 MySQL、Redis、RabbitMQ;`@WebMvcTest` 只起 DispatcherServlet、
> Controller、ControllerAdvice、拦截器、过滤器,Service 用 `@MockBean` 替掉,两秒起。
> 我要测的是 HTTP 边界上的翻译——401 的拦截器、400 的参数校验、409/403/404 的异常映射、traceId 头——
> 这些都在 MVC 层,起数据库对它们没有意义。

**"MutableClock 是什么,为什么不 Thread.sleep?"**
> 熔断器"打开 60 秒后自动恢复"如果用 sleep 测,一个用例 60 秒。`Clock` 是注入的(ClockConfig,ADR-006 的决定),
> 测试里给一个能手动拨的 Clock,`advance(Duration.ofSeconds(60))` 一行时间就过去了,用例 10 毫秒。
> 同样的手法让"超时 3000ms 被如实记录进 latency_ms"可以精确断言,而不是断言"大约 3 秒"。

**替代方案**(以上是默认选择,可按需改)
> 如果更信真库,`SlaOverdueQueryH2Test` 和 `MqMessageDedupH2Test` 两个类可以改成 Testcontainers 的 MySQL,
> 测试方法一行不用改,只换 `@H2SliceTest` 注解里的数据源配置。
