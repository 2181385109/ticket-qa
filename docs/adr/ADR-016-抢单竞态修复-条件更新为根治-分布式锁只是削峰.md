# ADR-016: 抢单竞态的修复——条件 UPDATE 是根治手段,version 是通用兜底,Redis 锁只是削峰

## 背景

第一版 `TicketService.grab` 是 SELECT → 内存判断 `status == PENDING` → `updateById`。
2026-09-20 压测([记录](../findings/20260920-压测-抢单并发重复分配.md))证明:
2 线程即 100% 复现重复分配,N ≤ 池内连接数 + 1 时 N 个请求全部 200,`assignee_id` 被逐个覆盖,
组长的手动指派也会被抢单覆盖。根因是 check-then-act:SELECT 是 REPEATABLE-READ 下的一致性
非锁定读(看到的是事务快照),UPDATE 才拿行锁;任何在第一个 COMMIT 之前完成 SELECT 的线程都会
读到 PENDING、通过判断、排进行锁队列,锁一释放就逐个覆盖。窗口宽度无竞争 12~13 ms,20 线程 28.8 ms。

修复必须回答两个问题:哪一层是"没有它就不正确"的,哪一层只是"有了它更好"。这两者混在一起讲,
就说不清哪一层是必须的。

## 选项

- **方案 A:条件 UPDATE** ← 采用(根治)
  做法:`UPDATE ticket SET status='ASSIGNED', assignee_id=?, version=version+1
  WHERE id=? AND status='PENDING' AND version=? AND deleted=0`,受影响 0 行即抛
  `IllegalTransitionException`(409/40901)。`TicketMapper.grabIfPending`。
  为什么它是根治:UPDATE 的 WHERE 是**当前读**(current read)——InnoDB 先拿行锁,再在最新已提交版本上
  求值谓词。N 个事务同时发这条语句,在行锁上排成队,第一个把 status 改成 ASSIGNED 并提交后,后面每一个
  拿到锁时重新求值 `status='PENDING'` 都是 false → 0 行。判断和写入在同一把锁下、同一条语句里完成,
  应用层没有任何"读到旧值"的窗口。它不依赖 Redis、不依赖时钟、不依赖任何进程外状态,单机多实例都成立。
  代价:一条手写 SQL;失败方拿到的是"0 行"而不是"为什么"——顺序场景(已被抢再抢)仍先用 SELECT
  判断给出准确文案,并发场景统一返回 40901。

- **方案 B:乐观锁 `version`** ← 采用(通用兜底)
  做法:`ticket.version` 列 + MyBatis-Plus `@Version` + `OptimisticLockerInnerInterceptor`,
  所有 `updateById` 自动变成 `... WHERE id=? AND version=?`,`SET version=?+1`;受影响 0 行抛
  `CONCURRENT_MODIFICATION`(409/40903)。
  它解决的是方案 A 覆盖不到的路径:`transit()`(WAIT_CONFIRM 上 CLOSED 与 PROCESSING 同时到)、`assign()`
  (改派与抢单撞车)、`update()`(改标题与流转撞车)、SLA 升级(扫描读到 PENDING、升级前被抢成 ASSIGNED)。
  这些路径的"判断"是状态机查表,不能像抢单那样把一个固定的 status 写进 WHERE,但可以把"我读到的版本"
  写进 WHERE——语义变成"只有这行和我读到时一模一样才允许我写",任何并发写入都会让它失败。
  代价:每张表多一列;冲突方需要客户端重读重试;单靠它做抢单会让"谁赢"取决于谁先 UPDATE 而不是谁先 SELECT,
  行为正确但排队的事务都白白进了库。

- **方案 C:Redis 分布式锁(SET NX PX)** ← 采用(削峰,fail-open)
  做法:`GrabLock`,key `ticketqa:lock:grab:{id}`,TTL 3 s,拿不到锁直接 409/40904,
  **不占数据库连接、不进行锁队列**;Redis 不可用时放行(fail-open)并打点 `grab_lock_unavailable_total`;
  释放用 Lua 比较 token 再 DEL,只删自己加的锁。锁在事务之外拿、提交之后放,所以 `grab()` 改用
  `TransactionTemplate`(注解式事务包不住这个顺序,同类自调用也不走代理,和 `create()` 是同一个理由)。
  它解决的是**性能**问题:修复前 20 线程抢同一张单,20 个事务全部排进行锁队列,第 12 个要等 160 ms、
  100 线程时 UPDATE 的 lock_time 阶梯到 226 ms;有了这一层,同一张单同一时刻只有 1 个请求进库,
  其余在拿到数据库连接之前就返回。回归实测 100 线程:进库 2 个、锁挡掉 98 个。
  为什么它**不能**是正确性保证:① Redis 不可用时要 fail-open(本项目 Redis 定位是加速器,ADR-006 的
  SLA 锁同样如此),fail-open 的一瞬间就没有锁;② TTL 到期锁自动消失,持锁者的事务若还没提交(连接池排满时
  最多等 5 s),后来者就能进库;③ 单节点 Redis 主从切换会丢锁。三种情况下都会有"多一个请求进库",
  此时兜住的是方案 A。回归里专门做了 **Redis 停机下的 20 / 100 线程集合点**:120 个请求全部 fail-open 进库,
  11 个走到条件更新拿到 0 行,结果仍是恰好 1 个 200——这就是"锁只是优化"的实证。

- 方案 D:`SELECT ... FOR UPDATE`
  做法:把读升级为锁定读,后续判断在锁内做。
  代价:所有抢单串行化在锁上,排队的事务照样占着连接等锁(和修复前的锁队列一样长),只是不会写错;
  等待时间进 P99。它等价于方案 A 的性能劣化版,没有理由选。

- 方案 E:`assignee_id` 唯一约束 / 唯一辅助表
  做法:`INSERT INTO ticket_grab(ticket_id) VALUES(?)` 唯一键冲突即失败。
  代价:多一张表、多一次写;它本质上还是"让数据库在锁下判断",和方案 A 同类但更绕。

## 决定

三层同时上,职责分明:

| 层 | 类 / SQL | 保证什么 | 失败码 | 指标 |
|---|---|---|---|---|
| 1 Redis 前置锁 | `GrabLock` | 削峰:同一张单同一时刻只放 1 个请求进库 | 40904 | `grab_lock_{acquired,rejected,unavailable}_total` |
| 2 条件 UPDATE | `TicketMapper.grabIfPending` | **正确性**:只有仍为 PENDING 的行会被改 | 40901 | `grab_conflict_total` |
| 3 version | `@Version` + 拦截器,所有 `updateById` | 其它写路径的正确性 + 审计 from 可信(ADR-017) | 40903 | `ticket_version_conflict_total` |

抢单那条语句里 2 和 3 合并在同一个 WHERE 里(`status='PENDING' AND version=?`)。

回归([记录](../findings/修复后回归验证.md)):2 线程 × 5 轮、20 线程、100 线程全部恰好 1 个 200,
审计 `to_status='ASSIGNED'` 恰 1 行,序列连续;Redis 停机下 20 / 100 线程同样恰好 1 个 200。
拐点压测抢单链路平台 486 QPS vs 修复前 489~501,创建链路 348 vs 365——多一次 Redis 往返的代价在
噪声量级内。

## 后果

- 接受:每次抢单多两次 Redis 往返(SET NX + Lua DEL),无竞争时约 +1 ms;Redis 停机时每次抢单多等
  500 ms(Redis 超时)再 fail-open。
- 接受:失败方的错误码分三种(40901 / 40903 / 40904),客户端要把三者都当"没抢到,刷新再看"处理。
  没有合并成一个码,是因为它们的**分布**是可观测的:`grab_lock_rejected_total` 大说明削峰在起作用,
  `grab_conflict_total` 大说明锁没挡住(Redis 不可用或 TTL 太短)。
- 接受:`reset_grabbed.py` 这类直接改库的压测工具不动 version,条件更新只要求它和 SELECT 读到的一致。
- 什么场景下这个选择会是错的:如果业务要求"抢单排队、谁先来谁得"而不是"谁先提交谁得",
  Redis 拒绝式的锁会让先到的请求被拒——那时该换成带等待队列的锁或消息队列。本项目抢单语义是"抢",
  拒绝即合理。
- 什么场景下 version 会成为负担:批量 UPDATE(比如 SLA 一轮升级 100 张)每张都要先读 version,
  已经是这么做的(逐张事务);若改成一条语句批量升级,version 要改成 `version = version + 1` 无条件递增
  并放弃逐行冲突检测。

## 常见质疑与回应

**Q:既然条件 UPDATE 就够了,为什么还要 Redis 锁?不是多此一举吗?**
> 正确性确实只需要条件 UPDATE。Redis 锁解决的是另一个问题:修复前 100 个请求抢同一张单,
> 100 个事务都要拿连接、都进行锁队列,UPDATE 的锁等待阶梯到 226 ms,而 99 个注定失败。
> 锁把这 99 个在拿到数据库连接之前就挡回去,回归里 100 线程只有 2 个进库。它是性能优化,
> 所以我让它 fail-open——Redis 挂了照样正确,只是慢一点;并且我用 Redis 停机下的 20 / 100 线程
> 集合点专门验证过这一点,120 个请求全进库,结果还是恰好 1 个 200。

**Q:为什么不直接只用分布式锁?很多项目就是这么做的。**
> 因为分布式锁给不了正确性保证。三个漏洞:Redis 不可用时要么 fail-open(那一刻没锁)要么 fail-close
> (Redis 一挂抢单全挂,和 Redis 是加速器的定位冲突);TTL 到期锁自动消失,持锁者事务还没提交别人就进来了;
> 主从切换会丢锁。Redlock 也只是把概率降低,不是消除。而条件 UPDATE 的正确性是 InnoDB 行锁给的,
> 单条语句、当前读,没有这些窗口。所以锁只能是优化,正确性必须落在数据库那条语句上。

**Q:为什么不用 SELECT ... FOR UPDATE?**
> FOR UPDATE 能保证正确,但它让所有抢单在行锁上串行排队,排队的事务照样占着连接——这和修复前的
> 锁队列一样长,只是不写错。条件 UPDATE 同样在行锁上排队,但每个事务只有一条语句、拿到锁后立刻判断
> 立刻结束,持锁时间最短;再加上 Redis 前置锁把大部分请求挡在库外,队列本身也没了。
> FOR UPDATE 是"正确但慢"的写法,没有它更好的场景。

**Q:乐观锁和条件 UPDATE 有什么区别?为什么两个都要?**
> 条件 UPDATE 把业务谓词写进 WHERE:`status='PENDING'`。它只适用于"我知道写之前必须是什么状态"
> 的场景,抢单正好是。乐观锁把"我读到的版本"写进 WHERE:`version=?`,它不关心业务语义,
> 只保证"这行和我读到时一模一样"。状态机流转的目标状态是查表得到的,前置状态不固定,写不出固定谓词,
> 但能写 version。所以抢单用前者(语义更强、失败信息更准),其它写路径用后者(通用)。
> 抢单那条语句两个都带,version 顺便保证了"标题被人改过"这种非状态变化也会让过期快照失败。

**Q:失败为什么返回 409 而不是 200 + 提示?**
> 抢单失败是资源状态冲突,HTTP 语义上就是 409。三个业务码分别表示被谁挡的:40904 是 Redis 锁挡在库外,
> 40901 是进库后条件更新发现已被抢,40903 是乐观锁发现快照过期。分开是为了可观测——
> `grab_lock_rejected_total` 和 `grab_conflict_total` 的比例能直接告诉我削峰层是否在工作。

**Q:你怎么证明修好了?"跑了一次没复现"不算证据。**
> 用定位时完全相同的手段回归:同一个 JMeter 集合点脚本、同样的档位(2 线程 × 5 轮、20、100),
> 每轮查库核对三件事——审计 `to_status='ASSIGNED'` 恰 1 行、审计序列首尾相接、终值 assignee 等于唯一的 200。
> 修复前这套手段是 12/12 轮复现,修复后 7/7 轮通过,再加 Redis 停机下 2 轮。并且把它做成了 pytest 门禁
> (`test_concurrency.py`,栅栏同步的多线程),每次 CI 都跑,断言"≥2 个 200 即失败"。
