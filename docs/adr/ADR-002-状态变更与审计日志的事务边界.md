# ADR-002: 状态变更、审计日志、MQ 发送、LLM 调用各自落在事务的哪一侧

## 背景

一次"流转工单"要做四件事:改工单状态、写审计日志、发 MQ 通知、(创建时)调 LLM 分类。
它们的失败模式完全不同:

- 改状态和写审计是同一个 MySQL,可以放在一个事务里原子提交;
- MQ 是另一个系统,没法参与 MySQL 事务;
- LLM 是一个最长 3 秒的 HTTP 调用,不该在事务里等。

CLAUDE.md §5.8 要求审计日志"用于数据一致性校验",§6 要求 `@Transactional` 显式写
`rollbackFor` 并在 ADR 里说明边界。这条 ADR 就是那个说明。

## 选项

### 审计日志和状态变更的关系

- **方案 A:同一事务** ← 采用
  做法:Service 方法 `@Transactional(rollbackFor = Exception.class)`,里面依次
  `updateById` + `auditLogService.record()`;`AuditLogService.record()` 用
  `Propagation.MANDATORY`——没有外层事务就直接抛异常。
  代价:审计写失败会导致状态变更一起回滚,业务操作失败。

- **方案 B:审计独立事务(REQUIRES_NEW)或异步写**
  做法:审计自己开事务,或丢到线程池 / MQ 异步写。
  代价:会出现"状态变了但没有审计"或"有审计但状态回滚了"的窗口,§5.8 的一致性校验
  就没有基准了。

### MQ 消息什么时候发

- **方案 A:事务内直接 `rabbitTemplate.send`**
  代价:消息先到、事务后回滚 → 消费者读到的是旧状态;或者消费者比事务提交更快,
  查库查不到新状态。

- **方案 B:事务提交后发送(`@TransactionalEventListener(AFTER_COMMIT)`)** ← 采用
  做法:Service 在事务里 `publishEvent(TicketDomainEvent)`,`TicketEventPublisher`
  在 AFTER_COMMIT 阶段把它转成 MQ 消息发出。
  代价:提交成功但发送失败,消息丢失。这里只记 ERROR 日志和打点
  `mq_event_publish_failed_total`,不做补偿。

- **方案 C:本地消息表 / Outbox + 定时投递**
  做法:事务里把消息写进 outbox 表,后台任务扫表投递,投递成功再标记。
  代价:多一张表、一个扫描任务、一套"投递中 / 已投递"状态;严格来说做到了"至少一次",
  但这个项目的消费端已经幂等(ADR-003),丢消息的后果是通知丢失而不是数据错误。

### LLM 调用在哪里

- **方案 A:在 `@Transactional` 的 create 方法里调用**
  代价:每次创建工单占着一个 HikariCP 连接等 LLM 最长 3 秒;连接池 20 个,JMeter
  并发一上来先耗尽的是数据库连接而不是 LLM——压测结果会失真。

- **方案 B:先调 LLM,再用 `TransactionTemplate` 开事务落库** ← 采用
  做法:`TicketService.create()` 本身不加注解,前半段调 `llmService.classify()`,
  后半段 `txTemplate.execute(...)` 里插工单、写审计、发事件。
  代价:用了编程式事务,和其他方法的注解式风格不一致;需要在代码里注释清楚为什么。
  (不能拆成同类里两个方法再加注解——自调用不经过代理,注解不生效。)

### LLM 调用记录在哪个事务

- `LlmCallLogService.record()` 用 `REQUIRES_NEW`:调用已经发生,不管工单事务成不成功,
  这条记录都要留下(它是"为什么分类错了 / 为什么慢"的唯一证据)。
- `bindTicket()` 用默认 `REQUIRED`:加入工单事务,工单回滚时绑定一起回滚,不会留下指向
  不存在工单的 `ticket_id`。

## 决定

| 动作 | 事务位置 | 传播行为 |
|---|---|---|
| 改工单状态 | Service 方法事务内 | REQUIRED |
| 写审计日志 | 同一事务 | **MANDATORY**(强制要求外层事务) |
| 发 MQ | 事务提交后 | AFTER_COMMIT 监听器 |
| 调 LLM(创建) | 事务之外 | 无事务 |
| LLM 调用记录 | 独立事务 | REQUIRES_NEW |
| LLM 记录绑定 ticket_id | 工单事务内 | REQUIRED |

审计日志语义(默认选择,可改):创建工单那条审计记录 `from=null → PENDING`,来源标为
`LLM`,备注写 LLM 分类结果和是否降级。理由:工单的分类、优先级、SLA 截止时间都是 LLM
路径决定的,这条记录让"每张工单必有一条 source=LLM 的创建记录,且对应一条 llm_call_log"
成为可校验的一致性规则。如果认为创建应算 MANUAL,改 `TicketService.create()` 里一个
枚举值即可,不影响其他逻辑。

## 后果

- 接受:审计写失败会让业务操作失败。这是有意的——宁可操作失败,也不要没有审计的状态变更。
- 接受:MQ 消息可能丢(事务提交后 broker 恰好不可用)。做故障注入 `docker stop rabbitmq`
  时会观察到:接口 200、状态已变、审计已写,但 `mq_event_publish_failed_total` 增长、
  消费端没有去重记录。这正是这个取舍的可观测后果。
- 接受:`create()` 用编程式事务,风格不统一。
- 什么场景下会是错的:如果通知是业务强依赖(比如通知触发下游结算),丢消息就不可接受,
  必须上 Outbox。本项目的通知只是"告诉人一声",丢了不产生错误数据。

> **2026-09-21 更新**:故障注入实测 RabbitMQ 停机期间 9 条消息永久丢失,与压测任务书"不丢、补投"的验收标准冲突。
> 决定维持本 ADR 的取舍、以"丢失可观测"替代补投,差异登记在 [ADR-018](ADR-018-MQ丢失可观测替代补投-规格差异登记.md),
> 并有用例断言"恢复后不补投"。另:审计的 `from_status` 现在只在 UPDATE 命中 1 行后写(乐观锁 / 条件更新),见 ADR-017;
> 抢单改用 `TransactionTemplate`(锁要在事务外拿),见 ADR-016。

## 常见质疑与回应

**Q:为什么不做 Outbox / 本地消息表?丢消息不是 bug 吗?**
> 先看丢消息的后果:我的三类消息都是通知,消费端只是打日志 + 写去重记录,丢了不会产生
> 错误数据,只是少一条通知。Outbox 要多一张表、一个扫描任务、一套投递状态,换来的是"通知
> 至少一次"。我把它记成一个已知取舍,并且让它可观测——`mq_event_publish_failed_total` 指标
> 和 ERROR 日志——而不是假装它不存在。如果通知变成强依赖,Outbox 是第一个要加的东西。

**Q:AFTER_COMMIT 里抛异常会怎样?**
> 事务已经提交了,异常不会回滚任何东西,只会往上冒。所以我在监听器里 catch 了
> `AmqpException`,记日志和打点,不让它冒到 Controller 变成 500——用户的操作明明成功了,
> 不能因为通知失败给他报错。

**Q:审计用 MANDATORY 有什么意义?REQUIRED 不也一样吗?**
> 行为上,在有事务的场景里两者一样。区别在没有事务的场景:REQUIRED 会悄悄自己开一个
> 事务,审计和状态变更就分家了;MANDATORY 会直接抛
> `IllegalTransactionStateException`,把"忘了加 @Transactional"这个 bug 在第一次调用时
> 暴露出来。它是把 ADR 里的约束变成代码里的断言。

**Q:LLM 调用为什么不能在事务里?反正最后都要落库。**
> 事务持有数据库连接。LLM 最长等 3 秒,连接池 20 个,意味着并发 20 个创建请求就把连接
> 池占满了,第 21 个请求在等数据库连接而不是等 LLM——压测的时候你会看到数据库连接超时,
> 以为是数据库瓶颈,其实是 LLM 慢。把 LLM 挪到事务外,数据库连接只在真正读写的几十毫秒
> 里被占用。

**Q:那为什么不拆两个方法,一个调 LLM,一个 @Transactional 落库?**
> 如果两个方法在同一个类里,`this.persist()` 不经过 Spring 代理,`@Transactional` 不生效——
> 这是 Spring AOP 最经典的失效场景。要么拆到另一个 Bean,要么用编程式事务。我选了
> `TransactionTemplate`,因为事务边界就在这个方法里、一眼能看到,不用跨类找。
