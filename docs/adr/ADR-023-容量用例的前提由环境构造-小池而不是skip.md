# ADR-023: 容量用例的前提由环境构造——用小连接池起服务,而不是前提不成立就 skip

## 背景

`test_capacity.py::test_consumer_not_starved_when_pool_saturated` 要测的是"HikariCP 被 HTTP 打满时,
共用同一个池的 MQ 消费者不能被饿死"(压测记录第 13 条)。它的前提是**池真的被打满**,
用例用 `hikaricp_connections_pending > 0` 断言这个前提。

开源仓库第一次 CI(2026-09-21,run 35563688456)这条用例失败,失败的正是前提断言,Allure 附件里的实测:

| | 本地(Windows 服务 ↔ WSL 里的 MySQL) | GitHub runner(ubuntu-22.04,全部 loopback) |
|---|---|---|
| 40 线程 × 8 s 产出 | 2641 张 ≈ 326 req/s | 1039 张 ≈ 127 req/s |
| `hikaricp_connections_pending` 峰值 | 7 | **0** |
| STATUS_CHANGED 队列深度峰值 | 2118 | **0** |
| 单次创建耗时 | 数百 ms | 13~23 ms |

原因不是 runner 慢,是**服务端太快、负载源太慢**:runner 上一次创建 ~15 ms,20 条连接的理论吞吐 > 1000 req/s;
负载源是同一台 4 vCPU 上、被 coverage.py 跟踪的 Python 40 线程,只打出 127 req/s,连一条连接都排不上队。
本地能打满是因为 Windows↔WSL 的每次创建要几百毫秒,40 个并发自然把 20 条占满。
这个前提在 GitHub runner 上靠加线程也到不了(GIL + coverage 开销,CPU 还被 JVM / MySQL / RabbitMQ / WireMock 分掉)。

所以问题变成:**一条依赖"环境能制造出某种压力"的用例,在制造不出压力的环境里应该怎么办?**
同一天刚处理过一条类似的用例:全库审计扫描在空库上 `skip`,结果它在 CI 里永远不跑(见 test-inventory 说明)。

## 选项

- **方案 A:让前提由环境构造——服务的池大小支持环境变量覆盖,CI 用小池(3 条)单独一步跑容量用例** ← 采用
  做法:`application.yml` 的 `maximum-pool-size` 改为 `${HIKARI_MAX_POOL_SIZE:20}`(默认值不变);
  CI 在主跑(`-m "not capacity"`,池 20,ADR-021 的预热照旧)之后,用 `HIKARI_MAX_POOL_SIZE=3` 重启服务、
  再预热、只跑 `capacity` 标记;两步的 Allure 结果合成一份报告。
  用例里的前提断言保留,失败消息带实测的池大小、pending 峰值、req/s。
  代价:CI 多一次服务重启(约 10 s)和一次 3 个用例的运行;`application.yml` 多一个只给测试用的环境变量;
  容量用例现在是在"3 条连接"这个人为条件下跑,它测的是机制(争池时消费不归零、停止后清得完),
  数字(消费速率、清空时长)只在同一池大小下可比。

- 方案 B:前提不成立就 `pytest.skip`,消息带实测数字,test-inventory 登记为环境相关
  做法:三行改动。
  代价:在 GitHub runner 上它**永远** skip——一条永远不跑的用例和没有这条用例没有区别,只是报告里多一行灰色。
  和刚修掉的审计扫描 skip 是同一个问题:skip 把"环境不满足"藏进了通过率的分母之外。

- 方案 C:把断言改弱——池没打满就只断"消费不归零 + 60 s 内清空"
  做法:去掉前提断言。
  代价:池没打满时"消费不归零"是必然成立的,这条用例在 CI 上退化成"MQ 能消费",和 `test_backlog_drains_without_loss`
  重复,而设计文档 08 里写的那个场景(争池)在 CI 上一次都没测到。

- 方案 D:CI 的 pytest 加 `-m "not capacity"`,容量用例只在本地跑
  代价:和 B 一样是"CI 不跑",只是换了个写法;还会连带把另外两条能在 CI 上正常跑的容量用例也排除。

- 方案 E:加大负载(线程 / 时长)
  代价:预计到不了(上面的算术),而且即使某次到了,也是把"打不打得满"寄托在 runner 那一刻的负载能力上,
  下次 runner 换机型又变回 0。前提应当是确定的,不是概率的。

## 决定

方案 A。原则是:**用例的前提由环境确定性地构造,不由用例猜、也不在前提不成立时静默退出。**
"池被打满"是一个可以直接设定的条件(池有多大),不需要靠打流量去"争取"。

小池只是**测试环境的设定**,不是生产配置:`maximum-pool-size` 的默认值仍是 20,
本地 `java -jar` 不带环境变量时行为不变;并发门禁(ADR-021)仍然在撑满的 20 条上跑,两者在 CI 里是两个 step、
两次服务启动,互不影响。

验证(2026-09-21):
- 本地 `HIKARI_MAX_POOL_SIZE=3` 起服务、`pytest -m capacity`:3 passed;饥饿用例实测 pending 峰值 33、
  池满期间消费 7 条/s(不为 0)、停止后 92 条/s、14.9 s 清空——争池场景真实出现,消费者变慢但没饿死。
- CI:见本 ADR 末尾的补记。

## 后果

- 接受:容量用例的消费速率 / 清空时长数字和压测记录(池 20)不可直接比,Allure 附件里现在带 `HikariCP max=`,
  平台层的基线对比会因环境状态不同把这类比较标为不可信(ADR-022),这是对的。
- 接受:`application.yml` 里多了一个环境变量。它的注释写明"只给测试用";如果有人在生产用它把池设小,那是配置管理问题,
  不是这条 ADR 能拦的。
- 什么时候这个选择会是错的:如果用例要测的是"**20 条连接**下的争池表现"(比如容量规划),小池就测不到目标——
  那时需要的是能打出 >1000 req/s 的负载源(JMeter,`tests/perf/`),而不是 pytest 里的 40 个 Python 线程;
  这条用例的职责是机制回归,不是容量规划。
- 如果 runner 变得更快、3 条连接也打不满(pending 仍为 0),前提断言会再次失败并在消息里给出 req/s 和池大小,
  届时把 `HIKARI_MAX_POOL_SIZE` 调到 2 或 1,不是放宽断言。

## 常见质疑与回应

**"改被测服务的配置来迁就测试,不是在作弊吗?"**
> 改的是一个可设定的环境参数,不是被测逻辑;默认值没变,生产路径没变。类比:测超时降级时把 WireMock 延迟设成 5 s,
> 也是在"构造前提"。作弊是改断言让它通过;这里断言一个字没动,前提不成立仍然红。

**"为什么不 skip?skip 也是 pytest 的正当用法。"**
> skip 的正当用法是"这个环境根本不适用"(比如 Windows 专属用例在 Linux 上)。这里环境完全适用,只是压力不够,
> 而压力是可以设定的。在能构造前提的情况下 skip,等于承认这条用例在 CI 里永远不跑。
> 一条永远不跑的用例和没有它没有区别——报告里多一行灰色,并不能证明什么。

**"小池下测出来的消费速率有意义吗?"**
> 数字本身只在同一池大小下可比,所以附件里带 `HikariCP max=`。这条用例断的是机制:争池时消费不归零、停止后清得完、
> 一条不丢。这三条在任何池大小下都应该成立,小池只是让"争池"真的发生。

**"为什么不干脆整套都在小池下跑?"**
> 并发门禁(ADR-021)要的恰恰相反:池越满、能同时进库的线程越多,对竞态修复越严苛。两类用例对池的要求相反,
> 所以分两步、两次启动。用例按 `capacity` 标记分流,不改用例本身。

**"多起一次服务,CI 变慢了多少?"**
> 一次启动约 10 s、预热约 1 s、三个容量用例本地 46 s。整个 api job 第一次跑是 5 分 11 秒,增加不到一分钟。
