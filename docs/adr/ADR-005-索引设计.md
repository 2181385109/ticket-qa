# ADR-005: 索引怎么建——哪些查询走哪个索引、是否回表

## 背景

六张表里只有 `ticket` 有多种访问路径,其余表要么只按主键 / 唯一键访问,要么只按 `ticket_id`
查。索引设计的核心问题是:**SLA 扫描、坐席看自己的单、组长看本组的单**这三条高频查询各走
哪个索引,以及每个索引的代价是否值得。

MySQL 8 InnoDB:主键是聚簇索引(叶子节点就是整行数据),二级索引的叶子节点存的是
索引列 + 主键值。通过二级索引找到主键后,还要再去聚簇索引取整行,这一步叫**回表**。
如果查询要的列全在二级索引里,就不用回表,叫**覆盖索引**。

## 选项(逐张表)

### ticket

| 查询 | SQL 关键条件 | 走的索引 | 是否回表 |
|---|---|---|---|
| SLA 扫描找超时单 | `status IN ('PENDING','ASSIGNED') AND escalated_at IS NULL AND sla_deadline <= ? AND deleted = 0 ORDER BY sla_deadline LIMIT 100` | `idx_ticket_status_sla (status, sla_deadline)` | 索引定位 + **少量回表**:SELECT 的 id 在二级索引叶子里,但 `escalated_at` 和 `deleted` 不在索引里,过滤它们要回表取行。这两列选择性极低(99% 为 NULL / 0),进索引只会徒增写放大;扫描每 30 秒一次、LIMIT 100,回表代价可忽略。EXPLAIN 若显示 rows 远大于 100,再把 `escalated_at` 加进索引 |
| SLA 条件更新 | `WHERE id = ? AND status IN (...) AND escalated_at IS NULL` | 主键 | 聚簇索引直接定位 |
| 坐席看自己的单 | `assignee_id = ? [AND status = ?] ORDER BY id DESC LIMIT` | `idx_ticket_assignee_status (assignee_id, status)` | 回表(要整行)。列表最多一页 20~200 行,回表代价可接受 |
| 组长看本组的单 | `group_id = ? [AND status = ?] ORDER BY id DESC LIMIT` | `idx_ticket_group_status_created (group_id, status, created_at)` | 回表。`created_at` 放进索引是为了未来按创建时间范围查(比如"本组今天的单")不用再加索引;当前 ORDER BY id 不能用它排序,会 filesort——一页数据量小,可接受 |
| 按单号查 | `ticket_no = ?` | `uk_ticket_no` | 回表。唯一键同时保证单号不重 |
| 按客户查 | `customer_id = ?` | `idx_ticket_customer` | 回表。本阶段没有这个接口,但它是客服系统最自然的查询,索引先建上 |
| ADMIN 看全部 | `[status = ?] ORDER BY id DESC LIMIT` | 主键扫描,或 status 单列不够选择性时全表 | 全表数据量小时无所谓;大表要加 `(status, id)` |

**为什么 `(status, sla_deadline)` 而不是 `(sla_deadline, status)`**:
`status IN (两个值)` 是等值条件,`sla_deadline <= ?` 是范围条件。复合索引的最左前缀原则下,
等值列在前、范围列在后,才能让两个条件都用上索引;范围列在前,后面的列就用不上了。
`status` 只有 6 个值、选择性很低,但作为前导等值列它把扫描范围缩到两个状态的分段内,
再在段内按 `sla_deadline` 范围扫,这是正确的顺序。

**为什么不给 `escalated_at` 建索引**:它 99% 为 NULL,`IS NULL` 条件的选择性极低,
建了 MySQL 也不会选它;放进复合索引也只是徒增写放大。

**为什么把 `sla_deadline` 存成列而不是查询时算 `created_at + INTERVAL`**:
`WHERE created_at + INTERVAL x MINUTE <= NOW()` 里 `created_at` 被函数包住,索引失效;
而且每个优先级的 x 不同,查询要写成 CASE,更没法走索引。创建时算好、存成列,
扫描就是一次纯索引范围查询。

## 决定

如上表。原则:

1. 每条已知的高频查询有且只有一个明确的索引路径,写在这张表里。
2. 复合索引列顺序:等值在前、范围在后、排序列最后。
3. 低选择性列(`deleted`、`escalated_at`)不进索引,回表过滤,用 EXPLAIN 验证扫描行数。
4. 不为"可能用到"的查询预建索引,`idx_ticket_customer` 是唯一的例外(客服系统的基本查询)。

## 后果

- 接受:`ticket` 表有 5 个二级索引,每次 INSERT / UPDATE status 要维护 3~4 个。工单表的写入
  频率远低于读,可接受。
- 接受:组长列表 `ORDER BY id DESC` 在 `(group_id, status, created_at)` 上会 filesort。
  一页 20 行,filesort 在内存里完成,毫秒级。如果要消除,把 `created_at` 换成 `id`——
  但那会失去按时间范围查的能力,两者选其一。
- 接受:ADMIN 看全部工单没有专用索引。数据量上万后会慢,那时加 `(status, id)`。
- 什么场景下会是错的:工单表上亿行、需要按多个维度组合筛选——那是 Elasticsearch 的活,
  不是再加几个 MySQL 索引能解决的。

## 常见质疑与回应

**Q:SLA 扫描这条查询回不回表?**
> 部分回表。查询只 SELECT id,而 InnoDB 二级索引的叶子节点存的是索引列加主键值,所以
> 拿 id 本身不用回聚簇索引。但 `escalated_at IS NULL` 和 `deleted = 0` 这两个条件的列不在
> `(status, sla_deadline)` 里,引擎要回表取这两列才能过滤——索引条件下推(ICP)只能用索引里
> 有的列,帮不上忙。要做到 EXPLAIN 显示 `Using index`(纯覆盖),得把它们加进索引,比如
> `(status, escalated_at, sla_deadline)`。我没这么做,因为这两列 99% 是 NULL 和 0,选择性极低,
> 加进去只会让索引变宽、每次状态更新多维护一份;而扫描每 30 秒一次、LIMIT 100,回表 100 行
> 是毫秒级。这个判断应该用 EXPLAIN 验证,findings 里贴真实输出,rows 远大于 100 就
> 把 `escalated_at` 加进去。

**Q:你为什么不直接把索引建全,让它覆盖?**
> 索引不是免费的。`ticket` 表上每加一列进索引,每次 UPDATE status 都要多写一份;而覆盖索引
> 省下的是每 30 秒回表 100 行。写放大是每次状态变更都付,回表是每 30 秒付一次,后者便宜
> 得多。索引设计是在读写之间做交换,不是把读优化到极致。

**Q:status 选择性那么低,为什么放在索引最前面?**
> 因为它是等值条件,`sla_deadline` 是范围条件。复合索引里范围列后面的列用不上,所以范围
> 列必须放最后。`status` 虽然只有 6 个值,但它把整个索引切成 6 段,扫描时只看 PENDING 和
> ASSIGNED 两段,每段内按 `sla_deadline` 有序——范围条件正好在有序段上走。反过来
> `(sla_deadline, status)`,先按时间范围扫,扫到的每一行再看 status,多扫 4/6 的无用行。

**Q:为什么不用 Redis ZSET 按 deadline 排序做 SLA 扫描?**
> 可以,但引入了第二份状态。工单状态在 MySQL,ZSET 里的 deadline 要在每次状态变更时同步
> 维护,任何一次同步失败就会出现"MySQL 说已处理、ZSET 还在等升级"的不一致。MySQL 一次
> 索引范围查询每 30 秒跑一次,对一张几万行的表就是几毫秒,不值得为它引入一致性问题。
