# ADR-019: `ticket_no` 的随机段从 32 bit 改为 64 bit——生日碰撞是必然事件,不是偶发

## 背景

压测 200 线程创建([记录 §5.3](../findings/20260920-压测-性能拐点与瓶颈.md))出现 2 个 HTTP 500:
`Duplicate entry 'T20260920-33818501' for key 'ticket.uk_ticket_no'`。第一版单号 = `"T" + yyyyMMdd + "-" + UUID 前 8 位`,
每天只有 32 bit 随机量。当天累计创建 n ≈ 9 万张时生日碰撞期望 ≈ n² / 2^33 ≈ 0.9 次,实测 2 次。
后果:客户的一次提交 500,工单没落库,而 LLM 已经调过一次并记了账。日均几万单的量级下这是必然事件(KI-011)。

## 选项

- **方案 A:随机段扩到 64 bit(16 个十六进制字符)** ← 采用
  做法:`TicketNoGenerator.generate` 用 `ThreadLocalRandom.nextLong()`,`Long.toHexString` 补零到 16 位。
  单号 `T20260921-80A053DF092749D5`,26 字符,列 VARCHAR(32) 不用改。同样 n = 9 万,期望碰撞 ≈ 2×10⁻¹⁰;
  要把期望推到 0.5 次,一天要创建 43 亿张。
  代价:单号变长 8 个字符;人眼不好念——但单号本来就不是给人念的,客服系统对外用的是 id。

- 方案 B:数据库自增 / 雪花 ID 作单号
  做法:单号 = 日期 + 自增序列,或 Snowflake(时间戳 + 机器 + 序列)。
  代价:自增序列要么用 `ticket.id`(那单号就没必要单独存了,还暴露业务量),要么另起一张序列表
  (每次创建多一次写,压测瓶颈就在写路径);Snowflake 要分配机器 id、处理时钟回拨,单体项目引入它是杀鸡用牛刀。
  两者都能用,但都比"把随机位数加倍"多出一层运维。

- 方案 C:碰撞时重试一次
  做法:捕获 `DuplicateKeyException`,换个随机数重插。
  代价:治标——32 bit 下 n = 9 万时碰撞率是每天 0.9 次,重试解决了这个 0.9,但 n 涨到 50 万时期望是 29 次,
  重试后再碰撞的概率也不再可忽略;而且重试要包在事务边界里,`create()` 的 `TransactionTemplate` 段要改成循环。
  把根因(位宽)修掉之后,重试就不需要了。

- 方案 D:去掉 `uk_ticket_no`
  不是选项:唯一键是最后一道防线,碰撞时宁可 500 也不能出两张同号单。

## 决定

方案 A,保留唯一键。随机源用 `ThreadLocalRandom` 而不是 `SecureRandom`:单号不承担鉴权(鉴权只认 X-User-Id),
不需要不可预测性;`SecureRandom` 在高并发下有锁竞争,创建链路的拐点就在数据访问层,没必要再加一处。

用统计把决定钉住(`TicketNoGeneratorTest`):同一毫秒生成 100 万个单号断言无重复;同一个测试里把第一版算法
留作对照,100 万次里断言**必然**碰撞(期望 116 次,P(无碰撞) ≈ e⁻¹¹⁶)。接口层再加一条 10 线程 100 张的唯一性 + 格式断言。

## 后果

- 接受:老数据的单号是 8 位随机段,新数据是 16 位,两种长度并存;`uk_ticket_no` 不区分长度,不冲突。
- 接受:接口自动化里原来的正则 `[0-9A-F]{8}` 改成 `{16}`;任何依赖单号长度的下游要改。
- 什么场景下这个选择会是错的:如果单号要给人念(电话报单号),64 bit 太长,应该换成"日期 + 短序列"
  并接受一次序列表写入的代价。

## 常见质疑与回应

**Q:UUID 不是全球唯一吗?怎么会撞?**
> UUID v4 是 122 bit 随机,撞不了;撞的是我截取的前 8 个十六进制字符——只剩 32 bit。
> 生日问题:32 bit 空间里放 9 万个随机数,期望碰撞 n²/2³³ ≈ 0.9 次,实测 2 次,完全符合。
> 教训是"截 UUID 前几位"这种写法看起来随机,位数一截就不够了。

**Q:为什么不用自增 id 或雪花?那才是标准做法。**
> 都能用,但都多一层东西:自增序列要一张序列表或直接暴露 id;Snowflake 要机器 id 和时钟回拨处理。
> 我的问题只是位数不够,把随机段从 32 bit 加到 64 bit,同样的日量碰撞期望从 0.9 降到 2×10⁻¹⁰,
> 一行代码、不加依赖、不加写入。等业务量到了 64 bit 也不够的那天——一天 43 亿张——再谈雪花。

**Q:100 万次的单测不是太重了吗?**
> 约 2 秒。它的价值是把一个概率论结论变成能跑的证据:同一个测试里 32 bit 必挂、64 bit 必过。
> 被问到"你怎么知道 64 bit 够"时,我可以说"我算过,也跑过"。如果嫌重可以降到 10 万次,
> 32 bit 那条对照的期望碰撞就只剩 1.2 次、有 30% 的概率不挂,对照就失去了说服力。
