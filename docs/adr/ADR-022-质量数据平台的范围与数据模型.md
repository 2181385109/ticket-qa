# ADR-022: 质量数据平台只做三件事;性能基线必须连同环境状态一起存,环境不同就不下结论

## 背景

第三阶段要一个"极简质量数据平台":执行记录入库、通过率 / 覆盖率趋势、性能基线对比。
明确不做用例管理、任务调度、权限、用户系统。真正需要决策的只有两处:
① 性能基线的数据模型——KI-010 证明同一代码在不同连接池状态下 QPS / 成功数都会变,平台如果只存 QPS / P99,
"本轮比基线掉了 5%"这句话没有意义;② 技术形态——一个要"能看就行"的前端,值不值得引入一套前端工程。

## 选项

### 基线的数据模型

- **方案 A:每轮压测存 JMeter 汇总 + 压测前完整环境快照(JSON 列),对比时先比环境再比指标** ← 采用
  做法:`qa_perf_run.env_json` 存 `env_state.py --json` 的整份输出;`PerfComparator` 先逐项比较池大小、堆上限、
  数据量(±20%)、后台 SLA 积压、MQ 积压(±1000)、MySQL 持久化配置、熔断状态,任一显著不同 → 结论 `UNRELIABLE`;
  环境一致才按阈值判 `RED` / `GREEN`。导入接口把 `env` 设为必填非空:没有环境的轮次拒收。
  代价:一列 JSON,每轮几 KB;"显著"的规则是硬编码的经验值,换一套压测工具要改比较器。

- 方案 B:只存指标,环境写在 note 里
  代价:note 是给人看的,机器比不了;三个月后没人记得那轮是不是在调度器积压 2.5 万张的背景下跑的——
  正是 2026-09-20 的记录里花了一整篇才讲清楚的事。

- 方案 C:环境状态拆成规范化的列(pool_total、heap_max、ticket_rows……)
  代价:`env_state.py` 采什么随着排障需要在变(这一轮就加了 Tomcat 线程数),每加一项改表改实体改导入;
  JSON 列 + 按键读取,新键自动存下、比较器按需读,老快照缺键跳过。

### 技术形态

- **方案 D:Spring Boot 后端 + 一张静态页(Vue 3 / Chart.js 走 CDN)** ← 采用
  代价:没有组件化、没有热更新、CDN 断网页面打不开;换来的是零构建、零 node_modules、仓库里没有 lock 文件,
  一个 `java -jar` 起完整个平台。规格说"UI 能看就行"。

- 方案 E:Vite + Vue 工程
  代价:node_modules、构建产物、两套启动流程;对一个三页面的看板是过度工程。

### 表放哪

- **方案 F:与被测服务同一个库,`qa_` 前缀,启动时 `CREATE TABLE IF NOT EXISTS`** ← 采用
  代价:平台数据和业务数据混在一个库里;换来的是不需要新的库和授权(MySQL 镜像只给 `ticketqa` 用户授了 `ticket_qa` 库),
  已有数据卷不用重建。压测清库脚本只 TRUNCATE 五张业务表,不碰 `qa_` 表。

## 决定

A + D + F。阈值:QPS 下降 ≥ 10% 或 P99 上升 ≥ 20% 标红(闭区间,和 SLA 的闭区间约定一致)。
10% / 20% 来自本项目两轮压测的抖动:修复前后同档位 QPS 差 −0.4% ~ −7%,P99 差 −17% ~ +13%,阈值放在抖动之外、
一档并发的差异之内(创建链路 20 → 50 线程 QPS +31%、P99 ×2.5)。它们是配置项,不是常量。

用 2026-09-20 / 09-21 的真实数据验证:六组"修复前 vs 修复后"对比全部 `UNRELIABLE`,差异项是起跑池 3 vs 11、
后台 SLA 积压 0 vs 3907~25590、MQ 积压相差数万——与 findings 里人工得出的"这 4% 不能坐实"完全一致。

## 后果

- 接受:平台上大部分对比会是黄色(UNRELIABLE)而不是绿或红,因为本机压测很难做到环境完全一致。
  这是诚实的结果:它逼着压测的人先控制环境,再谈退化。
- 接受:CDN 依赖;内网环境要把两个 js 文件放进 `static/` 改引用。
- 接受:没有认证,任何能访问 8081 的人都能导入 / 改基线。它和被测服务一样是测试系统,不是生产系统。
- 什么场景下这个选择会是错的:多人多项目共用时需要项目维度和权限;基线数量上千时 JSON 列上的过滤查询会慢,
  那时把比较器读的几个键抽成生成列加索引。

## 常见质疑与回应

**Q:性能对比不就是两个数相减吗?为什么要存一整份环境?**
> 因为我被这个坑过:同一份代码、同一个脚本、20 线程,不同时刻跑出 4 到 20 六种成功数,变的是连接池的历史状态。
> 拿其中两轮相减能得出任何结论。所以每轮压测前的环境状态——池、堆、后台任务积压、数据量、MySQL 配置——
> 必须和数字一起存,对比时先比环境:环境不一致,数字再难看也只显示"不可信",不显示"退化"。
> 这次导入修复前后的 12 轮,六组对比全部被判不可信,原因和我人工分析的一模一样。平台把这个判断自动化了。

**Q:阈值 10% / 20% 怎么来的?**
> 从抖动来:修复前后同档位、被判环境不同的两轮,QPS 差在 −0.4% 到 −7% 之间,P99 差 −17% 到 +13%。
> 阈值要放在这个抖动之外,又要在"一档并发"的差异之内(20 到 50 线程 QPS 差 31%)。10% 和 20% 落在中间。
> 它们是配置项,压测环境换了就要重新标定。

**Q:为什么不用现成的,比如 Grafana / Allure 的趋势?**
> Grafana 看的是运行时指标,不存"这轮压测的结论";Allure 的历史趋势只有通过率,没有性能基线,更没有环境状态。
> 我要的是"本轮 vs 基线 + 环境是否可比"这一个判断,三张表两个接口就够,引入一个平台反而要为它的数据模型妥协。

**Q:前端用 CDN 引 Vue 太随意了吧?**
> 规格说 UI 能看就行。三个页面、四个接口,Vite 工程的收益是组件化和热更新,代价是 node_modules 和第二套构建。
> 我把复杂度花在比较器的规则和它的单测上,那才是这个平台有价值的部分;页面只是把 JSON 画出来。

**Q:通过率为什么去掉 skipped 和 xfailed?**
> skipped 是"没跑",xfailed 是"预期失败且确实失败了"(已知问题挂在套件里,ADR-014),两者都不是这次执行对代码的判断。
> 算进分母,一个全绿但挂着 3 条已知问题的批次会显示 99%,趋势图上永远到不了 100,看图的人分不清是有失败还是有已知问题。
