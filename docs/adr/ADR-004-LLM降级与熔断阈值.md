# ADR-004: LLM 依赖的超时、熔断、契约校验阈值怎么定,哪些失败计入熔断

## 背景

工单创建时要调 LLM 做分类 + 优先级预测,坐席回复时要生成草稿。LLM 是一个
**慢、贵、输出不确定、可用性不由我控制**的依赖。CLAUDE.md §5.5 给了三个硬数字:
超时 3 秒、连续失败 5 次熔断 60 秒、分类越界落 OTHER。这条 ADR 记录这些数字背后的推理、
边界情况怎么归类,以及为什么不引 Resilience4j。

## 选项

### 超时怎么实现

- **方案 A:HTTP 客户端级超时(JDK HttpClient 请求 timeout = 3s)** ← 采用
  做法:`JdkClientHttpRequestFactory.setReadTimeout(3000ms)`,底层是 `HttpRequest.timeout()`,
  语义是"从发出请求到收到响应头"的整体超时。超时抛 `HttpTimeoutException`,
  `LlmHttpSupport` 识别后归为 `TIMEOUT`。
  代价:响应头到了、响应体慢慢滴(slow drip)的情况不受这个超时约束。分类响应体只有几十
  字节,这个风险可忽略。

- **方案 B:线程池 + `Future.get(3s)`**
  做法:把调用丢到线程池,主线程等 3 秒。
  代价:超时后工作线程还在等 HTTP,线程池会被慢请求填满;要额外管理线程池大小和拒绝策略;
  每次调用多一次线程切换。

### 熔断器

- **方案 A:自己写 40 行(连续失败计数 + 打开截止时间)** ← 采用
  做法:`CircuitBreaker` 类,`AtomicInteger` 计数,`volatile long openUntil`。
  连续失败 ≥ 5 → 打开 60 秒 → 到期自动闭合、计数清零。**没有半开状态**。
  代价:没有半开意味着 60 秒到期后第一批请求全部放行去探测;如果上游还没恢复,
  它们会再失败 5 次才重新打开——最多 5 次无效调用的浪费。

- **方案 B:Resilience4j CircuitBreaker**
  做法:引依赖,注解 `@CircuitBreaker(name=..., fallbackMethod=...)`。
  代价:它的状态机是 CLOSED / OPEN / HALF_OPEN 加滑动窗口(基于计数或时间),
  参数有十几个(`slidingWindowSize`、`failureRateThreshold`、`permittedNumberOfCallsInHalfOpenState`……),
  每一个都是额外的状态和参数,而规格只需要"连续 5 次"这一种策略。
  不在锁定的技术栈里。

### 哪些失败计入熔断器

| 情况 | DegradeReason | 计入熔断? | 走规则? | 理由 |
|---|---|---|---|---|
| 超过 3 秒 | TIMEOUT | 是 | 是 | 上游不可用的信号 |
| HTTP 5xx / 4xx / 连接失败 | UPSTREAM_ERROR | 是 | 是 | 同上 |
| 2xx 但响应体解析不出来 | BAD_RESPONSE | 是 | 是 | 模型不可用(输出格式崩了) |
| 熔断器打开期间 | CIRCUIT_OPEN | —(没发请求) | 是 | 直接走规则 |
| 2xx、JSON 合法、category 不在枚举内 | —(不算降级) | **否** | 否,落 OTHER | 上游可用,只是答错了 |
| 2xx、JSON 合法、priority 不在枚举内 | —(不算降级) | **否** | 仅 priority 用规则兜底 | 同上 |

契约越界不计入熔断:熔断器衡量的是"上游能不能用",不是"上游答得对不对"。一个模型每次
都返回 `SPAM` 并不代表它不可用——那是 prompt 或模型选型的问题,靠 `llm_contract_violation_total`
指标暴露,不靠熔断。

### 数字为什么是 3s / 5 次 / 60s

规格给的,但可以给出合理性:

- **3 秒**:创建工单是同步接口,用户在等。分类任务输出不到 20 个 token,正常 P99 在 1 秒内;
  3 秒是"正常慢"和"出问题了"的分界。超过 3 秒不如立刻用规则给一个确定结果。
- **5 次**:连续 5 次失败在正常流量下几乎不会偶然发生(单次失败率 1% 时,连续 5 次是 1e-10);
  它足够小到能快速止损,又足够大到不被单次抖动误触发。
- **60 秒**:上游 LLM 的故障恢复(限流窗口、实例重启)通常在分钟级;60 秒既让上游喘口气,
  又不会让降级持续太久以至于所有工单都被规则分到 OTHER。

## 决定

- 超时用 HTTP 客户端级 3 秒,不另起线程池。
- 熔断器自写,连续失败 5 次打开 60 秒,无半开。
- TIMEOUT / UPSTREAM_ERROR / BAD_RESPONSE 计入熔断并降级;契约越界不计入、不降级,
  category 落 OTHER,priority 用规则兜底。
- 熔断器**两个场景共用一个**(分类和草稿打同一个上游),`LlmService` 持有唯一实例。
- 指标:`llm_fallback_total{scene,reason}`、`llm_circuit_open_total{scene}`(每次打开计 1)、
  `llm_contract_violation_total{scene,field}`、`llm_call_duration_seconds{scene,outcome}`、
  `llm_circuit_state`(gauge,1=打开)。
- 每次调用一条 `llm_call_log`,含请求模型名、响应模型名、耗时、是否降级、原因、原始分类。

## 后果

- 接受:无半开状态,到期后最多浪费 5 次调用。
- 接受:熔断器状态在进程内存里,多实例各自独立;一个实例熔断了另一个可能还在打。
  本项目单体单实例,不是问题;多实例要么接受、要么把状态放 Redis(那又要处理 Redis 不可用)。
- 接受:契约越界不熔断,意味着一个"每次都答错"的模型会持续产生 OTHER 工单。
  靠指标告警发现,不靠代码自动处理——因为代码没法判断"答错"是模型坏了还是 prompt 该改了。
- 什么场景下会是错的:如果 LLM 是异步调用(比如创建工单后台分类),3 秒超时就太严了,
  可以放到 30 秒;如果有多个上游模型,需要每个上游一个熔断器。

> **2026-09-21 更新**:故障注入实测挡板恢复后熔断器仍固定降级到 60 s 到期(恢复后 +49 s 仍 open,+77 s 闭合)。
> 这是本 ADR 选"定值不探测"的直接后果,现在由 [ADR-020](ADR-020-故障恢复时长SLO与熔断定值.md) 写成显式接受的 SLO,
> 并有用例(`test_still_degraded_while_dependency_is_healthy`)把它钉住。带标签的 `llm_fallback_total` 等计数改为启动时预注册为 0(KI-007)。

## 常见质疑与回应

**Q:为什么不用 Resilience4j?它是标准做法。**
> 我的规格只需要一种策略:连续失败 5 次打开 60 秒。Resilience4j 提供的是滑动窗口 +
> 失败率 + 半开探测,那是另一套语义——它默认是"最近 100 次里失败率超 50%",不是"连续 5 次"。
> 要用它实现我的规格得调好几个参数,调完了行为还不完全一样。40 行代码我能在白板上把
> 状态转换画出来,每一行都能解释;换成框架,被问到"半开状态放行几个请求"时,我得去查文档。

**Q:没有半开状态是不是设计缺陷?**
> 是一个有意的简化。半开的作用是"用少量请求探测,避免恢复瞬间的流量冲击"。我这里到期后
> 全放行,最坏情况是上游还没好、再失败 5 次、再打开——浪费 5 次调用,每次最多 3 秒,
> 而且这 5 次都会正常降级到规则,用户无感。用这个代价换掉一个状态和一个参数,我觉得值。
> 如果上游是按调用计费且很贵,半开就该加回来。

**Q:分类越界为什么不算失败?模型明明答错了。**
> 因为熔断器回答的问题是"要不要继续发请求",不是"答案对不对"。答错的模型还是能用的——
> 它可能只是这一条工单描述太模糊。如果把越界计入熔断,一批模糊工单就能把熔断打开,
> 接下来 60 秒所有工单都走规则,包括那些模型本来能答对的。我把越界单独打点
> `llm_contract_violation_total`,它涨得快就是 prompt 或模型该换了,这是人的决策不是代码的。

**Q:超时 3 秒是怎么定的?**
> 规格给的,但我能解释它合理:这是同步接口,用户在等;分类只输出十几个 token,正常
> 1 秒内;3 秒是正常慢和出问题的分界。更重要的是超时后有一个确定的兜底——规则分类——
> 所以宁可超时早一点。如果没有兜底,超时就得设得很宽。

**Q:priority 越界为什么不也落一个固定值?**
> category 越界落 OTHER 是规格要求,而且 OTHER 语义上就是"归不了类"。priority 没有对应
> 的"不知道"值——落 P2 会让紧急工单被延后,落 P0 会让所有越界都变紧急。规则分类器有自己
> 的优先级判断(关键词),用它兜底比拍一个固定值合理。
