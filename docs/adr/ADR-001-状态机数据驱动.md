# ADR-001: 工单状态机用"枚举 + 流转表"数据驱动,不用 if-else

## 背景

工单有 6 个状态、9 条合法流转边、1 条带时间条件的边(CLOSED → PROCESSING 限 7 天内)。
状态流转是这个系统里最容易出 bug、也最容易被测试覆盖的部分:每条非法边都应该被
Service 层拦截并抛 `IllegalTransitionException`。

这张表要能画在白板上,并从表直接推导出"合法路径用例 + 非法流转用例"。
如果流转规则散落在 `if (status == PENDING && target == ASSIGNED)` 这类判断里,
既画不出表,也没法证明"其余一律非法"这句话真的成立。

## 选项

- **方案 A:if-else / switch 堆砌在 Service 方法里**
  做法:每个流转接口里写自己的判断。
  代价:规则散落,加一条边要改多处;"其余一律非法"没有单一出处,只能靠测试穷举验证;
  白板上讲不清。

- **方案 B:枚举 + 流转表(`Map<from, Set<to>>`)+ 守卫表 + 进入动作表** ← 采用
  做法:`TransitionTable` 里用 `EnumMap<TicketStatus, EnumSet<TicketStatus>>` 把 CLAUDE.md §5.1
  那六行原样抄进代码;附加条件(7 天重开)放在 `Map<Transition, TransitionGuard>`;
  进入某状态的固定副作用(清 assignee、记 closedAt)放在 `Map<TicketStatus, BiConsumer>`。
  `TicketStateMachine.transit()` 只做"查表 → 跑守卫 → 改状态 → 跑动作"四步。
  代价:多了三个类;守卫和动作是 lambda,Java 弱的读者要先理解函数式接口。

- **方案 C:Spring StateMachine 框架**
  做法:引 `spring-statemachine-core`,用 DSL 配置状态、事件、guard、action。
  代价:引一个重量级框架来管 6 个状态;它的线程模型(默认异步 sendEvent)和持久化
  (需要 StateMachinePersister)都是额外的复杂度,却和本项目的测试主题无关;
  CLAUDE.md §3 技术栈是锁定的,它不在列表里。

## 决定

方案 B。表是唯一事实来源,`TransitionTable.edges()` 暴露只读视图,测试和文档可以直接
从表推导:`hasEdge(from, to) == false` 的组合就是非法流转用例集合,总共 6×6 − 9 = 27 种
(含 6 种自流转)。

附带决定:
- 守卫返回 `Optional<String>`(拒绝原因)而不是 boolean,原因直接进异常消息。
- 进入动作在 `setStatus` **之前**执行,所以动作里 `ticket.getStatus()` 还是 from 状态,
  PROCESSING 的动作靠这一点区分"从 CLOSED 重开"和"从 WAIT_CONFIRM 打回"。
- 7 天重开按闭区间:`closedAt + 7d >= now` 允许,与 SLA 的闭区间约定(ADR-006)一致。
- "流转到 ASSIGNED 必须有 assignee"没有做成守卫,放在 Service 里用 `ASSIGNEE_REQUIRED(400)`
  报错——它是参数问题不是状态问题,错误码语义不同。

## 后果

- 接受:三个 Map 比一段 if-else 多几十行;新人第一次看要花 10 分钟理解 guard/action 的调用时机。
- 接受:表里没有"事件"概念(比如 `START_PROCESSING`),接口直接传目标状态。
  如果以后一个目标状态对应多种业务动作(比如"退回"和"撤销分配"都到 PENDING 但审计文案不同),
  这个设计会不够用,那时需要在表里加一层 `Event → (from, to)`。
- 什么场景下这个选择是错的:状态数超过 15、边上带复杂的多字段条件、需要层级状态或并行状态
  ——那是状态机框架的场景,不是 Map 的场景。

## 常见质疑与回应

**Q:为什么不用 Spring StateMachine?**
> 6 个状态 9 条边,一张 EnumMap 就是全部规则,引框架是在用大炮打蚊子。更重要的是,
> 我要在这上面推导测试用例——表就是用例的来源,`hasEdge` 为 false 的组合就是 27 个非法
> 用例,我能在白板上把它画出来。换成框架的 DSL,规则在配置类里,推导过程就不透明了。
> 而且 Spring StateMachine 的 sendEvent 默认是异步的、状态要单独持久化,这两点在我的
> 场景里都是负担,不是收益。

**Q:if-else 有什么不好?你这三个 Map 不也是判断吗?**
> 区别在"规则在哪里"。if-else 的规则和执行逻辑混在一起,加一条边要找到所有相关分支;
> 数据驱动的规则是一份数据,执行逻辑是四步固定流程,加边只改数据。我能证明"其余一律
> 非法"——因为不在表里的组合 `hasEdge` 必然返回 false——if-else 版本证明不了,只能靠测试穷举。

**Q:守卫为什么不返回 boolean?**
> 返回 boolean 的话,异常消息只能说"不允许从 CLOSED 到 PROCESSING",用户不知道是因为
> 超过 7 天还是别的原因。返回 `Optional<String>` 让拒绝原因跟着规则走,异常消息直接引用它。
> 空 Optional 表示放行,这也是 Java 里表达"可能没有值"的惯用法,比返回 null 安全。

**Q:7 天为什么是闭区间?**
> 和 SLA 用同一套约定(ADR-006),边界值用例只需要理解一次。恰好第 7 天允许重开、
> 恰好到时限算超时。选开区间也行,但必须只选一种并写进文档,否则边界值用例没有依据。
