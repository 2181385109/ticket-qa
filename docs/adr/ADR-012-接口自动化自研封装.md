# ADR-012: 接口自动化用 pytest + requests 自研封装,不用 HttpRunner / 关键字驱动框架

## 背景

CLAUDE.md §3 锁定"Python + pytest + requests(自研封装,禁用 HttpRunner)",§2.1 要求回答"为什么自研"。
禁用是前提,但"自研成什么样"仍是决策:封装的层次、断言怎么写、造数和清理怎么做、环境怎么切。
本项目的接口有几个特殊之处决定了封装的形状:

1. 统一信封 `{code, message, data, traceId}`,错误码前三位 = HTTP 状态——这是契约,断言应该长成契约的样子。
2. LLM 路径的关键事实(是否降级、模型名)**不在响应里**,在 `llm_call_log` 表和 Prometheus 指标里
   (docs/findings/20260920 的教训)。用例必须能同时对接口、库表、指标、挡板请求日志四处取证。
3. 熔断器是进程内状态,60 秒内影响所有 LLM 用例,用例之间有隐式耦合。
4. 数据要可重复:每个用例自己造、自己清,清理必须是硬删(接口的 DELETE 是逻辑删)。

## 选项

- **方案 A:HttpRunner / 类似的 YAML 关键字驱动框架**
  做法:用例写成 YAML,`validate: [eq: [status_code, 201]]`。
  代价:四处取证(DB / 指标 / WireMock 日志)要写自定义 debugtalk 函数,YAML 里调 Python,
  逻辑被劈成两半;"熔断用例排最后 + 等待恢复"这种编排在 YAML 里表达不了;
  断言失败信息是框架的,不带 traceId,排查要再去翻日志。CLAUDE.md 已禁用。

- **方案 B:裸 requests + pytest,每个用例自己拼请求、自己 `assert resp.status_code == 201`**
  做法:不封装。
  代价:X-User-Id 头、Content-Type、耗时统计、Allure 附件每个用例重复;断言失败只有一行
  `assert 403 == 201`,没有响应体;造数清理散落各处,漏一处就污染下一次运行。

- **方案 C:薄封装——四层 + 三个旁路工具 + 三层 fixture** ← 采用
  做法(`tests/api/framework/`):
  - `config`:`TICKETQA_ENV` 选 `local` / `ci`,env 文件 + 真实环境变量覆盖,不引 YAML 依赖
  - `client.ApiClient`:统一鉴权头、`as_user()` 换身份、每个请求自动挂 Allure 附件、测耗时;
    业务接口只做 URL/body 拼装,**不做断言**(断了状态码就没法测 409)
  - `response.ApiResponse + Expect`:链式断言 DSL,`resp.expect.error(403, 40301)` 一次断
    HTTP 状态 + 业务码 + 前三位一致 + data 为空 + traceId 一致;失败信息自动带请求摘要、响应体、traceId
  - `factory.TicketFactory`:走真实接口造到指定状态(`in_status("ESCALATED")`),记住 id,用例结束硬删五张表
  - 旁路:`db`(pymysql)、`wiremock`(管理 API:收到了什么请求、临时桩)、`metrics`(Prometheus 文本解析,按差值断言)、`mq`(管理 API 重投消息)
  - fixture 三层:session(配置、客户端、就绪检查)/ module(只读共享数据)/ function(工厂 + 指标快照)
  - `pytest_collection_modifyitems` 把 `circuit` 标记的用例排到最后
  代价:约 600 行框架代码要维护;新人要先读 framework 才能写用例(有 walkthrough 第 14 节)。

## 决定

方案 C。设计上只坚持一条原则:**接口层面看不出的事,用旁路证据断言;断言失败时排查所需的信息要在错误信息里。**

几个具体取舍:

- **不用 jsonschema**:响应字段少且固定,`has_keys` / `lacks_keys` 够用;schema 文件会和 VO 双份维护。
- **不用 pytest-ordering 插件**:排序需求只有一个(circuit 最后),一个 hook 十行解决。
- **不用 pytest-xdist 并行**:熔断器和 SLA 扫描都是进程内全局状态,并行会让用例互相影响;
  全套 4 分钟,其中 60 秒是等熔断恢复,并行省不了这 60 秒。
- **清理用硬删而不是每个用例回滚事务**:被测的是另一个进程,测试拿不到它的事务;
  硬删按 ticket_id 关联五张表,漏表会在下一次运行的计数断言里暴露。
- **标题 token 只用 a-f 字母**:唯一性够,又不会碰到关键词规则里的 `404` / `500` 和挡板正则里的 `error`。

## 后果

- 接受了:framework 是项目代码,要有自己的测试信号——所以 CI 里对它量 coverage.py 并做增量门禁(ADR-011)。
- 接受了:用例和这个服务的契约强耦合(错误码规则、信封字段),换一个服务要改 `response.py`;
  这是有意的,通用性不是目标。
- 接受了:不并行,总时长随用例数线性增长;超过 10 分钟时再考虑按标记拆成多个 job。
- 什么场景下这个选择是错的:如果测试团队多数人不写 Python、只填表格,关键字驱动的可读性会赢;
  本项目的接口自动化以 Python 为主,不成立。

## 常见质疑与回应

**"HttpRunner 也能做到这些,为什么要自己写?"**
> 能做到,但做到的方式是把逻辑劈成 YAML 和 debugtalk.py 两半。这个项目的核心断言是"响应说分类是 REFUND,
> 但 llm_call_log 说这次降级了"——它要同时看接口和库表。自研封装里这是一个用例里的两行;关键字框架里是
> YAML 调一个自定义函数再回来比较,可读性反而差。另外 CLAUDE.md 明确禁用了它。

**"自研封装是不是重复造轮子?"**
> 造的不是 HTTP 客户端,requests 已经是轮子。造的是这个服务的**契约**——错误码前三位等于 HTTP 状态、
> traceId 头和体一致、错误时 data 为空——这些没有现成轮子。`Expect.error(403, 40301)` 一行断五件事,
> 用通用框架要写五个 validate。

**"断言 DSL 为什么不直接 assert?"**
> 因为失败信息。`assert resp.status_code == 201` 失败时只有 `403 != 201`,要重跑一次加打印才知道响应体。
> DSL 里每个断言失败自动带上请求摘要、响应体、traceId、耗时——traceId 直接去服务日志 grep。
> 排查一次省的时间就超过写 DSL 的时间。另外每一步都记 Allure step,报告里能看到断言链走到哪一步断的。

**"为什么造数走接口不直接 INSERT?"**
> 直接 INSERT 造出来的工单没有审计日志、没有 llm_call_log、没有 MQ 消息,和真实数据不同构;
> 用它去测"审计条数 == 流转次数"是自欺。走接口造的数据就是用户造的数据。
> 只有时间旅行(把截止时间拨到过去、把关闭时间拨到 8 天前)才直接改库,因为接口没有这种能力。

**"清理为什么不用接口 DELETE?"**
> 接口的 DELETE 是逻辑删(`deleted=1`),行还在,`count_tickets()` 这类断言会被历史数据干扰,
> 而且逻辑删只碰 ticket 表,审计和去重表留着。硬删五张表才是"没跑过一样"。
> 代价是测试账号需要 DELETE 权限——它本来就是隔离环境的账号。

**"熔断用例污染怎么处理?"**
> 三层:① 每个降级用例结束做一次成功调用,把连续失败计数清零(fixture `reset_streak`);
> ② 熔断本身的用例打 `circuit` 标记,collection hook 排到会话最后;
> ③ 熔断模块开始前和结束后都等 `llm_circuit_state` 指标回到 0。
> 没有给服务加"重置熔断器"的管理接口——那是为了测试改被测代码,而且线上多一个能重置熔断器的接口是风险。

**"fixture 为什么分三层?"**
> 按"谁会改它"分。配置、客户端、就绪检查整个会话不变,session 级建一次;
> 只读的共享工单 module 级,一个文件的读用例共用,省造数时间;
> 会被改的工单 function 级,谁改谁造谁清。分错层的症状很明显:module 级的数据被某个用例改了状态,
> 后面的用例莫名其妙失败,而且和执行顺序有关。

**替代方案**(以上是默认选择,可按需改)
> 如果更想要并行,把 `circuit` 和 `sla` 标记的用例拆到单独的串行 job,其余加 `pytest-xdist -n 4`;
> 工厂已经按用例隔离数据,并行下不会互相清理。
