# ADR-018: RabbitMQ 停机期间的消息——规格要求"不丢、补投",实现放弃,以"丢失可观测"替代(规格差异登记)

## 背景

故障注入([记录 §2](../findings/20260920-故障注入记录.md))实测:`docker compose stop rabbitmq` 期间提交的
3 次操作共 9 条事件,接口全部成功、状态和审计全部落库,但消息永久丢失、恢复后不补投,`mq_event_publish_failed_total`
停在 9。这和 ADR-002 的设计一致(AFTER_COMMIT 发送,失败只记 ERROR + 打点,不做 outbox),
但**压测任务书的验收标准写的是"不丢、能补投"**。两者矛盾,必须二选一,而且不能靠改任务书把矛盾抹掉。

决定(2026-09-21):**选「丢失可观测」,不实现补投。** 本 ADR 登记这个差异:规格是什么、实现是什么、
为什么接受、用什么用例把"接受"钉住。

## 选项

- **方案 A:丢失可观测(维持 ADR-002)** ← 采用
  做法:不改代码。用例 `test_fault_injection.py::TestRabbitOutage` 断言四件事:停机期间业务不 500 且事务已提交;
  `mq_event_publish_failed_total` 增加;ERROR 日志逐条写明 type / ticketId / messageId;**恢复后 10 秒去重表仍为空**
  (明确断言"没有补投")。最后一条是关键——它把"不补投"从遗漏变成契约,将来谁实现了 outbox 这条用例会红,
  提醒同时改本 ADR。
  代价:通知确实会丢;丢失率 = broker 不可用时长 × 发送速率(本机抢单峰值 920 条/s,停 30 秒丢约 2.7 万条通知)。

- 方案 B:本地消息表 / Outbox + 定时投递
  做法:事务里把消息写进 outbox 表,后台任务扫表投递,成功后标记;消费端已幂等(ADR-003),重复投递无害。
  代价:一张表、一个扫描任务、一套投递状态、投递延迟(扫描周期);每次状态变更多一次 INSERT——
  压测瓶颈就在数据访问层的连接持有时间(30~43 ms/事务),再加一条写会把抢单平台从 ~490 QPS 往下拉;
  以及"至少一次"语义要求所有消费者永远幂等,这一点本项目已满足但要写进契约。

- 方案 C:RabbitMQ 发布确认(publisher confirms)+ 内存重试队列
  做法:开启 confirm,nack / 超时的消息放进内存队列,broker 恢复后重发。
  代价:进程重启内存队列就没了,只能覆盖"broker 短暂不可用"而不是"服务也重启了";实现复杂度不比 outbox 低,
  保证却弱。

- 方案 D:把验收标准改成"不丢"并声称已满足
  这不是选项。规格写了什么就是什么,实现没做到就登记差异。

## 决定

方案 A。三类消息的消费端行为是打日志 + 写去重记录(通知客户 / 坐席 / 组长),丢失不产生错误数据,
不触发下游结算。用例把"可观测"和"不补投"同时钉住;README §9 和 ADR-002 §后果 已经写明这个取舍,
本 ADR 补的是"规格与实现不一致"这一行本身。

**差异登记表**

| 项 | 内容 |
|---|---|
| 规格来源 | 2026-09-20 压测与故障注入任务书:RabbitMQ 停机"消息不丢、恢复后补投" |
| 实现行为 | 事务提交后发送,失败记 ERROR + `mq_event_publish_failed_total`,不补投(ADR-002 方案 B) |
| 差异 | 停机期间的事件永久丢失 |
| 决定 | 接受差异;以可观测替代补投 |
| 决定日期 | 2026-09-21 |
| 钉住的用例 | `tests/api/test_fault_injection.py::TestRabbitOutage::test_publish_failure_is_observable_and_not_replayed` |
| 何时重新评估 | 任一消费者从"通知"变成"业务动作"(触发结算、改库存、发外部消息) |

## 后果

- 接受:通知丢失;运维靠 `mq_event_publish_failed_total` 的告警和 ERROR 日志里的 messageId 知道丢了哪些。
- 接受:任务书和实现的差异永久存在于文档里,要主动写明而不是等人发现。
- 什么场景下这个选择会是错的:通知一旦变成业务强依赖(丢一条 = 少一笔结算),必须上 outbox;
  届时 ADR-002 的 MQ 一节和本 ADR 一起作废,用例改成断言"恢复后补投 N 条"。

## 常见质疑与回应

**Q:规格要求不丢,你没做到,为什么不修?**
> 因为修的代价和收益不匹配。丢的是通知,不是数据——工单、审计、状态全部完整,消费端只是打日志。
> 上 outbox 要一张表、一个扫描任务、每次状态变更多一次写,而压测已经证明瓶颈就在每事务的连接持有时间,
> 多一次写会直接压低抢单的平台 QPS。我把这个差异登记下来:规格是什么、实现是什么、什么条件下要重新评估,
> 并且用一条用例把"不补投"钉成契约。规格和实现不一致时,登记差异比假装一致诚实,也比盲目补齐便宜。

**Q:那这条用例断言"没有补投",不是在测一个缺陷吗?**
> 它测的是一个**决定**。如果哪天有人顺手实现了 outbox,这条用例会红,逼他同时改 ADR——
> 和 ADR-014 里用 xfail(strict) 挂已知问题是同一个思路:让文档和代码互相约束,而不是各说各的。

**Q:可观测到底观测到了什么?丢了就是丢了。**
> 三个层面:指标 `mq_event_publish_failed_total` 可告警;ERROR 日志每条带 type / ticketId / messageId,
> 能精确知道丢了哪几条、属于哪些工单;健康检查 rabbit=DOWN 能定位时间窗。有这三样,事后人工补通知是可行的;
> 没有这三样,连丢没丢都不知道——这才是最坏的状态。

**Q:发布确认(confirm)开一下不就行了?**
> confirm 只能告诉我 broker 没收到,收不到之后怎么办才是问题:重试队列放内存,进程一重启就没了;
> 放磁盘,那就是 outbox。confirm 是 outbox 的一部分,不是替代品。
