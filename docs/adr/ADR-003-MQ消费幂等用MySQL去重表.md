# ADR-003: MQ 消费端幂等用 MySQL 消息去重表,不用 Redis setnx

## 背景

RabbitMQ 的投递语义是"至少一次":消费者 ack 前崩溃、网络抖动、Broker 重启、本项目配置的
本地重试(最多 3 次)——任何一种都会让同一条消息被消费两次。
消费端必须幂等,CLAUDE.md §5.4 指定用 MySQL 去重表,并要求讲清楚为什么不用 Redis。

## 选项

- **方案 A:Redis `SET key NX EX`**
  做法:消费前 `setnx msg:{id}`,成功才处理。
  代价:Redis 的 setnx 和 MySQL 的业务写不在一个事务里。时序:setnx 成功 → 业务抛异常 →
  消息重投 → setnx 失败 → 消息被当作"已处理"跳过 → **这条消息永远丢了**。
  要补救就得在业务失败时 `DEL key`,但进程崩溃时 DEL 没机会执行;加 TTL 兜底又引入
  "TTL 过期后重复消费"的新窗口。另外 Redis 是内存,重启丢数据(除非开 AOF),去重记录
  没有可查的历史。

- **方案 B:MySQL 去重表 `(message_id, consumer)` 唯一键,和业务同事务** ← 采用
  做法:`IdempotentConsumerSupport.consumeOnce()` 开事务,先 `INSERT` 去重行,
  `DuplicateKeyException` → 已处理,返回;插入成功 → 执行业务;业务抛异常 → 整个事务回滚,
  去重行一起消失,消息重投后还能正常处理。
  代价:每条消息多一次 INSERT;去重表会增长,需要按 `consumed_at` 定期清理(本项目不做)。

- **方案 C:业务本身设计成天然幂等,不要去重表**
  做法:比如"通知已发送"用 `UPDATE ... WHERE notified = 0`。
  代价:三类消费者要各自设计幂等条件;本项目的消费者是"发通知",通知本身没有可比对的
  业务状态,做不成条件更新。

## 决定

方案 B。要点:

1. 唯一键是 `(message_id, consumer)` 而不是只有 `message_id`:同一条消息被不同消费者
   各处理一次是正常的(未来可能有第二个消费者订阅同一队列的副本)。
2. `message_id` 由**生产端**生成(UUID),写在消息体里。不用 RabbitMQ 的 delivery tag——
   那是每次投递不同的,重投时会变。
3. 去重行和业务在**同一个本地事务**里。这是整个方案的核心,也是它比 Redis 强的唯一理由。
4. `DuplicateKeyException` 在 `tryMark()` 内部 catch,不让它穿出 `@Transactional` 边界,
   否则 Spring 会把事务标记为 rollback-only。MySQL 里一条失败的 INSERT 不会让事务失效,
   可以继续用(PostgreSQL 会,那里要用 savepoint 或 `INSERT ... ON CONFLICT DO NOTHING`)。
5. 消息消费失败的策略:`default-requeue-rejected=false` + 本地重试 3 次,重试用尽后消息被丢弃。
   没有死信队列——这是有意的简化,如果需要观察"毒消息",加一个 DLX 绑定即可。

## 后果

- 接受:每条消息多一次 INSERT,去重表随消息量线性增长。三个消费者、一张工单最多产生
  4~6 条去重记录,这个量级不需要考虑分区。
- 接受:没有清理任务。生产系统需要按 `consumed_at` 保留 N 天。
- 什么场景下会是错的:消费量每秒上万、业务写在别的库或根本不写库(纯计算 / 纯转发)——
  那时去重表成了瓶颈,且"同事务"的优势不存在,Redis + 业务幂等设计更合适。

## 常见质疑与回应

**Q:为什么不用 Redis setnx?它更快。**
> 快是真的,但它解决不了我最在意的那个窗口:setnx 成功之后业务失败,消息重投回来
> setnx 说"已经处理过了",这条消息就永远丢了。要补救得在失败时删 key,但进程崩溃的时候
> 删不了。MySQL 去重表和业务在同一个事务里,业务失败去重记录一起回滚,重投回来能正常
> 处理。我用一次 INSERT 的代价换一个没有漏洞的幂等,这个交换划算。

**Q:那你在 Redis 里加 TTL 不就行了?**
> TTL 是在两个错误之间选:TTL 太短,消息处理慢一点就重复消费;TTL 太长,失败的消息要等
> 很久才能重试。而且 TTL 到期后重复消费的窗口一直存在,只是被推迟了。同事务的方案没有
> 这个窗口。

**Q:message_id 为什么生产端生成?RabbitMQ 自己不是有 message id 吗?**
> AMQP 协议里有 `message_id` 属性,但默认是空的,得生产端填。我直接放在消息体里,理由是
> 消息体是 JSON、可读、跟着消息走到任何地方(日志、管理台、Python 脚本)。delivery tag
> 不能用,它是每次投递的序号,重投时会变。

**Q:唯一键为什么要加 consumer?**
> 同一条消息被不同消费者处理是合法的。今天三个队列各一个消费者,消息不会串;但如果以后
> 一条 `status.changed` 消息同时被"通知客户"和"更新报表"两个消费者订阅,只按 message_id
> 去重会让第二个消费者永远收不到。加 consumer 列是为了让去重的粒度对齐"谁处理"而不是
> "什么消息"。

**Q:重试 3 次后消息丢了,你能接受?**
> 这是通知消息,丢了不产生错误数据。我记了 ERROR 日志、去重表里没有记录、
> `mq_event_consumed_total` 不增长——三个可观测点。如果要保留毒消息做事后分析,配一个死信
> 交换机是 5 行配置的事,我没做是因为本项目里没人消费死信队列。
