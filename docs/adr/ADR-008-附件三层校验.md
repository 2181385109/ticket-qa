# ADR-008: 附件校验分三层——扩展名白名单、声明 MIME 一致、文件头魔数一致

## 背景

白名单 `jpg / png / pdf / txt`,单文件 ≤ 5MB,落本地目录,文件名重命名为 UUID。
CLAUDE.md §5.7 要求"同时校验扩展名和 MIME",安全用例要测绕过。
"MIME"在 HTTP 上传里有两个来源:客户端在 multipart part 里**声明**的 `Content-Type`,
和从文件内容**识别**出来的真实类型。前者一句 `curl -F 'file=@shell.php;type=image/jpeg'`
就能伪造,后者才是防绕过的关键。

## 选项

- **方案 A:只看扩展名**
  代价:`shell.php` 改名 `shell.jpg` 直接过。这是所有绕过用例的第一个。

- **方案 B:扩展名 + 客户端声明的 Content-Type**
  代价:声明是客户端说了算,`;type=image/jpeg` 就伪造了。比方案 A 只多拦"忘了改
  Content-Type 的攻击者"。

- **方案 C:扩展名 + 声明 MIME + 文件头魔数三层都过** ← 采用
  做法(`AttachmentService.upload`,从便宜到贵):
  1. 非空、`size <= 5MB`(闭区间,恰好 5MB 允许——和 SLA 的边界约定一致)
  2. 扩展名 = 原始文件名最后一个点之后、转小写,必须在白名单
  3. 声明的 `Content-Type`(去掉 `;charset=` 参数)必须等于扩展名对应的 MIME
     (`jpg→image/jpeg`、`png→image/png`、`pdf→application/pdf`、`txt→text/plain`),
     `application/octet-stream` 也不接受
  4. 读前 8KB,`FileTypeSniffer` 按魔数识别:`FF D8 FF`=jpg、`89 50 4E 47 0D 0A 1A 0A`=png、
     `25 50 44 46`=pdf;txt 没有魔数,要求**不含 NUL 字节、能严格按 UTF-8 解码、且不命中
     任何已知魔数**。识别结果必须等于扩展名。
  代价:每次上传多读 8KB、多一次 UTF-8 解码;txt 的判定是启发式的,一个纯 ASCII 的
  `<?php ... ?>` 会被当成合法 txt——但它以 `.txt` 落盘、UUID 命名、不在 Web 根目录,
  没有执行路径。

- **方案 D:引 Apache Tika 做内容识别**
  代价:Tika 核心包 1MB+,能识别上千种格式,而白名单只有 4 种;不在锁定的技术栈里;
  它的识别逻辑是黑盒,说不清"为什么这个文件被判成 jpg"。四条魔数 + 一个 UTF-8
  解码器,40 行代码,每一行都能解释。

### 附带决定

- **原始文件名永远不参与路径**:落盘名是 `UUID.ext`,原始名只进 `ticket_attachment.original_name`。
  路径穿越(`../../etc/passwd`)、双扩展名(`a.jpg.php`)、空字节截断在这里都没有意义——
  扩展名取最后一个点之后,`a.jpg.php` 的扩展名是 `php`,第 2 层就拦了。
- **Spring 的 `max-file-size` 设为 8MB**,比业务上限大:让"文件过大"由第 1 层以
  `ATTACHMENT_TOO_LARGE(41301)` 返回,而不是被容器层拦成没有业务错误码的 413。
  超过 8MB 才会触发 Spring 的 `MaxUploadSizeExceededException`,`GlobalExceptionHandler`
  也把它翻译成同一个错误码。
- **错误码区分层次**:`ATTACHMENT_EXT_NOT_ALLOWED(41502)` 是第 2 层,
  `ATTACHMENT_MIME_MISMATCH(41503)` 是第 3、4 层(消息里说明是"声明不符"还是"内容不符")。
  绕过用例可以精确断言被哪一层拦下。
- **上传权限**:走 `AccessChecker.checkWrite`,AGENT 只能给自己的工单传附件。
- 不做病毒扫描、不做图片重编码(去 EXIF / 去多态文件)。后者是防"图片里藏 PHP"的
  正规手段,但本项目的附件不会被任何解释器执行,做了没有观测点。

## 决定

方案 C,四步校验顺序固定,声明 MIME 和魔数都必须与扩展名一致。

## 后果

- 接受:`application/octet-stream` 被拒。有些 HTTP 客户端默认用它,调用方必须显式设
  Content-Type。README 的 curl 示例带 `;type=`。
- 接受:txt 的判定是启发式;一个合法 UTF-8 文本文件如果恰好以 `%PDF` 开头会被判成 pdf、
  与 `.txt` 不符而被拒——这是极端情况,可接受。
- 接受:魔数只看前几个字节,一个"jpg 头 + PHP 尾"的多态文件能过。它以 `.jpg` 落盘,
  不会被执行;要防这个得重编码图片,本项目不做。
- 什么场景下会是错的:附件会被下游解释器处理(比如用户上传的 SVG 会被浏览器渲染、
  PDF 会被服务端解析)——那时魔数校验不够,需要内容清洗或沙箱。

## 常见质疑与回应

**Q:同时校验扩展名和 MIME,MIME 指的是什么?客户端声明的不是可以伪造吗?**
> 对,所以我做了两个 MIME:声明的和识别的。声明的 Content-Type 一句 `;type=` 就伪造,
> 它只能拦"不会伪造的人";真正防绕过的是第四层——读文件头看魔数。jpg 是 FF D8 FF,
> png 是 89 50 4E 47,pdf 是 %PDF,这些是文件格式规范定的,改扩展名改不了它。
> 三层都过才收,用例可以分别打每一层。

**Q:为什么不用 Tika?自己写魔数不专业。**
> 白名单只有四种格式,三条魔数加一个 UTF-8 解码器,40 行。Tika 是为"识别任意文件"设计的,
> 能认上千种格式,但我不需要认、只需要"是不是这四种之一"。而且 Tika 的判定是黑盒,
> 被问到"这个文件为什么被判成 jpg"时,我得去翻它的源码;自己写的每一个字节我都能解释。
> 如果白名单扩展到几十种,Tika 就值得引了。

**Q:txt 没有魔数,你怎么校验?**
> 三个条件:不含 NUL 字节(二进制文件几乎都有)、能严格按 UTF-8 解码(用 REPORT 模式,
> 遇到非法序列直接失败而不是替换成问号)、不命中其他魔数(一个 PDF 改名 .txt 会被前一步
> 认出来)。它是启发式的,我承认一个纯 ASCII 的 PHP 脚本能过——但它以 .txt 落盘、UUID
> 命名、不在 Web 根目录,没有任何东西会执行它。校验的目标是"存进来的东西是它声称的
> 类型",不是"存进来的东西无害"。

**Q:5MB 是闭区间还是开区间?**
> 闭区间,恰好 5MB 允许,和 SLA 的约定一致(ADR-006)。Spring 自己的上传上限我设成 8MB,
> 比业务上限大,这样 5MB 到 8MB 之间的文件由我的业务校验以明确错误码 41301 拒绝,而不是
> 被容器层拦成一个没有业务语义的 413。边界值用例:5MB 整、5MB+1 字节、8MB+1 字节三个点。

**Q:文件名为什么要改 UUID?保留原名不是更友好?**
> 原始文件名是攻击面:路径穿越、超长文件名、特殊字符、双扩展名都从这里来。改成 UUID
> 之后原名永远不参与路径拼接,这些攻击就没有意义了。原名存在数据库里,下载时可以在
> Content-Disposition 里还给用户,友好性不受影响。
