# ADR-021: 并发用例的可复现性——先把连接池撑满,断言"≥2 个 200 即失败"而不是具体个数

## 背景

压测([记录](../findings/20260920-压测-同一并发不同成功数-连接池历史状态.md))发现同一脚本、同一代码、同一机器,
20 线程抢单在不同时刻得到 4 / 6 / 9 / 12 / 15 / 18 / 20 六种成功数:成功数 = 那一刻 HikariCP 池里已有的连接数 + 1,
池满后恒等于 `maximum-pool-size`。池是懒增长 + 10 分钟空闲收缩的,压测数字里混着"池的历史状态"这个隐藏变量。

修复后"成功数恒为 1"不再随池变化,但**能同时进库的线程数**(进而 40901 / 40904 的分布、锁的削峰量)仍然随池变化。
把并发用例放进每次 CI 的门禁,就必须回答:CI runner 上刚起的服务(池 = minimum-idle 2)和本地压测后的服务(池 20),
同一条用例怎么得到可比的结果?

## 选项

- **方案 A:用例前预热池到上限 + 只断言正确性不断言分布** ← 采用
  做法:`framework/pool.py::warm_pool` 用 max-pool-size + 5 个线程同时打一个占连接的只读接口(列表查询,
  不用 `/agents/me`——它命中 Redis 缓存后不碰数据库),让 Hikari 一次把池涨满,再读 `hikaricp_connections` 确认;
  CI 里在 pytest 之前跑 `tests/tools/warm_pool.py`,并发用例再通过 `warmed_pool` fixture 确认一次。
  断言只写"恰好 1 个 200(≥2 即失败)+ 审计恰 1 行 + 序列连续",三层计数只断言恒等式
  `acquired + rejected + unavailable == 线程数`,不断言 rejected 是 18 还是 19。
  代价:预热约 1 s;分布不断言意味着"削峰层失效"(比如 Redis 挂了、全部进库)不会让用例红——但那时
  `grab_lock_unavailable_total` 会涨,由指标而不是用例负责。

- 方案 B:固定池大小(`minimum-idle = maximum-pool-size = 20`)
  做法:HikariCP 官方推荐的固定池,池永不收缩。
  代价:常驻 20 条 MySQL 连接;它改变所有压测数字(修复前的全部记录是在收缩池下测的),要么全部重测,要么以后
  的数字和历史不可比。作为**运行配置**它可能是对的,但作为**测试可复现性手段**它把问题转移了——
  CI 上服务刚启动池也是满的,本地开发者的服务也是,但换一台把 `minimum-idle` 改回去的机器就又不可比了。
  预热是在用例侧解决,不依赖被测配置。

- 方案 C:断言具体分布(比如 20 线程 = 1 个 200 + 1 个 40901 + 18 个 40904)
  代价:进库的线程数 = min(线程数, 池大小 + 1) 中"+1"取决于 Hikari 异步建连的速度,Windows→WSL 是几十毫秒,
  Linux 同机是几毫秒,同一条断言在两种环境上给出不同的数。这正是压测记录警告的"把环境状态当结论"。

- 方案 D:mock 掉连接池 / 用嵌入式数据库跑并发用例
  代价:竞态窗口的宽度就是真实数据库的行锁 + fsync 时间,换成 H2 内存库窗口变成微秒级,"同时"反而更难制造;
  而且它测不到 HikariCP 和 InnoDB 的真实行为——正是这两者决定了修复前后的差异。

## 决定

方案 A。预热是"让隐藏变量取一个已知值",断言收窄是"不把隐藏变量的取值当结论"。
每条并发用例的 Allure 报告里都挂着预热后的池大小和三层计数,分布仍然可见,只是不作为通过条件。

同一原则也用于容量用例(`test_capacity.py`):断言"不丢、不重复、预算内清完",不断言"消费速率 ≥ 190/s"——
190 是本机 Windows↔WSL 的数字,CI 上的 runner 会给出另一个数,两者都记进报告。

## 后果

- 接受:预热让 CI 多 1 s;`warmed_pool` 断言"total ≥ max",若某天 `maximum-pool-size` 改成 100 而 MySQL
  `max_connections` 不够,预热本身会失败——这是好事,它暴露配置不一致。
- 接受:用例发现不了"削峰层没生效"这类性能退化;性能退化由压测 + 平台层的基线对比负责(ADR-022)。
- 什么场景下这个选择会是错的:如果并发用例的目的变成"验证削峰比例"(比如 SLO 要求 95% 的请求不进库),
  就必须断言分布,那时要同时固定池大小和 Redis 状态,并接受它只在一种环境上成立。

## 常见质疑与回应

**Q:预热连接池不是在"作弊"让用例更容易过吗?**
> 恰恰相反,池满时能同时进库的线程最多,竞态窗口里的竞争者最多,是对修复**最严苛**的条件。
> 修复前池满时 20 线程 20 个全部 200;修复后同样条件恰好 1 个。预热是把用例固定在最难的那一档,
> 而不是随机落在 4 个还是 20 个进库。

**Q:为什么不直接固定池大小?HikariCP 官方就推荐固定池。**
> 作为运行配置它可能对,但它改变所有压测数字,修复前的全部记录都是在收缩池下测的,改了以后前后不可比。
> 而且它把可复现性寄托在被测服务的配置上——换一台机器改回去,用例又不可比了。在用例侧预热不依赖任何被测配置,
> CI 和本地、改没改池大小,都从同一个起点跑。

**Q:只断言"1 个 200",分布不管,那 Redis 锁失效你怎么知道?**
> 用例负责正确性,指标负责性能。Redis 锁失效时 `grab_lock_unavailable_total` 涨、`grab_conflict_total` 涨,
> 这两个数每条用例都挂在报告里,平台层的基线对比也看它们。把"18 个 40904"写进断言,在 Linux 同机部署上
> 会变成 19 个——不是修复退化了,是建连快了。断言环境相关的数字等于把环境当被测对象。

**Q:那压测里那六种结果,你到底怎么向人解释"修好了"?**
> 修复前:成功数 = 池大小 + 1,六种结果六种池状态,每一种都是重复分配。修复后:任何池状态下成功数恒为 1,
> 我在池 = 2、3、20 三种状态下都验过,加 Redis 停机两轮。"修好了"的定义是"结果不再依赖那个隐藏变量",
> 不是"某一次跑出了 1"。
