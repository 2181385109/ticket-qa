# ADR-011: 增量覆盖率门禁 80%、全量兜底线 70/60,而不是 100%

## 背景

CLAUDE.md §3 要求 JaCoCo + coverage.py,§2.1 点名要回答"增量覆盖率门禁阈值为什么不是 100%"。
CI 要在合并前挡住"新代码没测"的提交,同时不能让门禁变成大家绕着走的形式主义。
三个量要定:门禁量的是什么(全量还是增量)、阈值多少、分母里放什么。

实测基线(2026-09-20,`mvn verify`,310 个单测):排除项之后 **行 90.8% / 分支 88.2% / 方法 86.1%**;
未覆盖的集中在四个 Controller(Web 切片只覆盖了 TicketController)和 `LlmClientConfig`。

## 选项

- **方案 A:全量覆盖率门禁,阈值定在当前值附近(比如 90%)**
  做法:`jacoco:check` BUNDLE LINE ≥ 0.90。
  代价:分母是整个代码库。一次提交如果加了 200 行没测的胶水代码,全量只掉 1~2 个点,
  门禁可能不响;反过来重构删掉一批已测代码,全量可能掉到线下,门禁响了但和这次改动无关。
  它量的是"历史积累",不是"这次提交"。

- **方案 B:增量覆盖率门禁(只看本次 diff 里的行)+ 一条低的全量兜底线** ← 采用
  做法:CI 里 `diff-cover` 读 JaCoCo XML,对比基线分支(PR 用 base 分支,push 用 HEAD~1),
  改动行的覆盖率 ≥ 80% 才过;`jacoco:check` 另设行 70% / 分支 60% 的全量下限,
  只防"整批删测试"这种极端情况。
  代价:增量覆盖率对"改了一行配置"这种提交会因为样本太小而剧烈波动(1 行没测就是 0%);
  需要工具支持(diff-cover 支持 JaCoCo XML 和 coverage.py XML,两边共用一套)。

- **方案 C:增量 100%**
  做法:同 B,阈值 100%。
  代价:见"后果"——它会把门禁变成对抗。

## 决定

方案 B。数字:**增量 80%(行)**;全量兜底 **行 70% / 分支 60%**;
Python 侧对 `tests/api/framework` 用 coverage.py 出 XML,同样的 diff-cover、同样的 80%。

分母的排除项(`service/pom.xml` jacoco `<excludes>`),每一条的理由:

| 排除 | 理由 |
|---|---|
| `TicketQaApplication` | 只有一行 `SpringApplication.run`,测它等于起整个容器 |
| `domain/entity/**`、`**/dto/**`、`mq/message/**`、`AgentSnapshot` | 全是 getter/setter/record;被其他测试间接覆盖到多少纯属巧合,数字没有信息量 |
| `config/**`、`LlmClientConfig` | `@Bean` 方法和 `@ConfigurationProperties` record,正确性靠启动而不是靠单测 |
| `OpenAiCompatibleLlmClient` | 真实供应商客户端,单测里没有任何理由去调 DeepSeek |

这些都不是"不重要所以不测",而是"测它得到的数字不能说明任何事"。留在分母里只会把有意义的数字稀释,
再拿稀释后的数字去定阈值就是自欺。

## 后果

- 接受了:增量 80% 意味着**允许每次提交有 20% 的改动行没被单测碰到**。这 20% 是留给
  日志语句、防御性分支、`catch` 里只打日志的代码——为了让它们绿而写的测试,通常只是在"调用一下"。
- 接受了:全量兜底线 70/60 离实际值(90/88)有 20 个点的余量,它几乎不会响。它的作用是让
  "把测试目录删了"这种操作过不了 CI,不是日常门禁。
- 接受了:push 到 main 时基线是 `HEAD~1`,如果一次 push 带多个 commit,只比最后一个。
  想严格就走 PR。
- 什么场景下这个选择是错的:如果项目进入"只改不加"的维护期,增量门禁大部分时候没有样本,
  真正的退化会体现在全量上——那时应该把全量线抬到实际值减 5 个点,让它真的参与守门。

## 常见质疑与回应

**"为什么不是 100%?"**
> 覆盖率是"代码被执行过"的比例,不是"代码被验证过"的比例。把阈值定到 100%,团队会为最后那几个百分点写
> 只调用不断言的测试——`catch (IOException e) { log.warn(...) }` 这种分支被覆盖到,对质量的贡献是零,
> 但它会让数字变绿。100% 的门禁在实践里换来的是覆盖率通胀,而不是更少的缺陷。
> 80% 是我给"值得写断言的代码"留的比例,剩下 20% 我宁可让它露着,让 review 的人看得见。

**"那 80 这个数怎么来的?为什么不是 70 或 90?"**
> 不是算出来的,是对着这个项目的实际分布定的:剔除实体、DTO、配置后,单测把业务代码覆盖到 90% 以上,
> 剩下没覆盖的就是 Controller 的透传方法和纯日志分支。80 比实际值低 10 个点,给了正常提交的波动空间;
> 再低就挡不住"整个方法没测",再高就开始逼人测日志。它是一个可以随项目调整的经验值,
> 重要的是它守的是**增量**——每次提交自己负责自己的行。

**"为什么增量而不是全量?"**
> 全量量的是历史。一个 5000 行、覆盖率 85% 的项目,加 100 行没测的代码,全量掉到 83.4%,
> 阈值 80 不会响;反过来删掉 500 行已测的老代码,全量可能跌破线,门禁响了却和这次改动无关。
> 增量量的是这次 diff 里的行,响了就是这次的问题,能直接指到行号。全量只留一条很低的线,
> 防的是"删测试目录"这种极端操作。

**"排除实体和 DTO 是不是在美化数字?"**
> 恰恰相反,是为了不让数字被美化。getter/setter 被随便哪个测试间接碰一下就算覆盖,
> 留在分母里会把真实业务代码 90% 和一堆巧合的 100% 混在一起。我要的数字是"业务逻辑被测了多少",
> 所以分母里只放业务逻辑。排除清单写在 pom 里,每一项都有理由,可以逐条质疑。

**"Python 那边为什么也要量?测试代码还要测试?"**
> `tests/api/framework` 不是用例,是封装层——断言 DSL、造数工厂、DB / WireMock / 指标客户端。
> 它有分支(比如 `Expect.error` 里"错误码前三位等于 HTTP 状态"的判断),这些分支被用例走到了才说明封装是在被使用而不是摆设。
> 用 coverage.py 量它、用同一个 diff-cover 门禁,成本只是 CI 里多两行;
> 收益是当有人往 framework 里加了没人用的方法时,增量覆盖率会把它指出来。

**"diff-cover 是 Python 工具,为什么用它处理 Java 的覆盖率?"**
> 因为它同时认 JaCoCo XML 和 coverage.py XML,两种语言一套门禁、一个阈值、一种报告。
> Java 生态里做增量的是 SonarQube 那类平台,本项目不引入服务端(CLAUDE.md §8);
> 也有 Gradle/Maven 插件方案,但只覆盖 Java 一边。diff-cover 在 CI 里就是一条 `pip install` 加一条命令。

**替代方案**(以上是默认选择,可按需改)
> 如果不认可 80,改 `.github/workflows/ci.yml` 里的 `DIFF_COVER_FAIL_UNDER` 和 pom 里的
> `jacoco.line.minimum` / `jacoco.branch.minimum` 即可,不需要动别的。
